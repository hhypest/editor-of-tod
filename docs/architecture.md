# Границы будущей платформы

Этот документ описывает целевое направление. Сейчас реализованы создание проекта без прежнего файла, импорт JSON, координатная рабочая область и SQLite-реестры на компьютере одного составителя; построение полного листа и согласование остаются следующими этапами.

## Исходная идея

Схема — самостоятельный версионируемый документ. Её данные состоят из параметров места работ, выбранного шаблона, размещённых объектов, реквизитов листа и сведений об источниках. В будущем геометрия печатного листа и PDF должны выводиться из этой модели; состояние интерфейса (выделенный объект, открытая вкладка, масштаб просмотра) хранится отдельно. Такой подход позволит одинаково проверять интерактивный лист, сохранённый JSON и печатный результат.

| Область             | Ответственность                                                    | Появление |
| ------------------- | ------------------------------------------------------------------ | --------- |
| Предметная модель   | Единицы измерения, данные схемы, версия JSON, инварианты           | Этап 1    |
| Нормативные профили | Версия источника, параметры шаблонов, правила предупреждений       | Этап 1    |
| Каталоги            | Переезды, знаки, происхождение и дата актуальности данных          | Этапы 1–2 |
| Редактор            | Состояние UI, команды, выделение, перетаскивание, отмена           | Этап 2    |
| Представление листа | Координатный просмотр, затем печать, PDF/PNG и эталонные сравнения | Этап 2    |
| Согласование        | Редакции, замечания, роли, статусы и аудит                         | Этап 3    |

Модули внедряются по мере необходимости. Текущий процесс Node.js обслуживает локальный интерфейс и SQLite только на `127.0.0.1`; это не сервер совместной работы. Отдельный сервер для организаций и механизм входа выбираются лишь после описания участников, состава данных, режима доступа и требований к хранению.

## Данные схемы

Формат хранения должен явно включать `schemaVersion`, идентификатор и дату версии нормативного профиля, выбранный шаблон, измеренные параметры, реквизиты и список объектов. У справочной записи переезда должны быть источник, дата сверки и отдельный идентификатор; копия значимых исходных значений сохраняется в редакции схемы, чтобы обновление каталога не переписало исторический документ. Текстовые подписи и реальные размеры хранятся отдельно. Команды редактора работают с моделью, а генератор листа получает неизменяемый снимок редакции.

Старый проект из HTML использует `v: 1`, условные координаты и признаки `auto`. Импорт переводит v1/v2/v3 в `schemaVersion: 4`; исходный v1 JSON остаётся в поле `source.originalJson`. Новый проект фиксирует ручное происхождение данных переезда, содержит измерения только выбранного варианта и не создаёт знаков автоматически. Составитель может отдельно закрепить ограниченный снимок локальной карточки ПУ-66 после сравнения; её дальнейшее изменение не переписывает схему. Изменения параметров и объектов применяются к снимкам v4; история отмены и повтора хранится только в памяти браузера. Явное сохранение записывает полные снимки в локальную SQLite, а восстановление старого снимка создаёт новую редакцию без изменения прежней. Номер ожидаемой редакции защищает от перезаписи изменений другой вкладки. Рабочая область использует условные координаты и исходные локальные PNG для знаков; она не является печатным листом. Дальнейшие проверки и печатный лист описаны в [контракте формата](scheme-format.md).

Локальные реестры разделены на карточки ПУ-66, краткие записи о нормативных пунктах и каталог знаков; черновики схем хранятся отдельно в той же базе. Импорт ПУ-66 хранит исходный XLSX в SQLite вместе с извлечёнными строками и источником каждой редакции. Отдельная ограниченная выборка возвращает поля для снимка схемы и номер редакции; после явного выбора составителем эти поля записываются в JSON. Знаки хранятся как две версии исходного PNG. Нормативный профиль пока не привязан к схеме; исходные PDF, полные тексты норм и рабочие карточки в публичный код не включаются.

## Согласование

Возможная последовательность состояний: черновик → внутренняя проверка → направлено участникам → замечания или согласовано → финальная редакция → архив. Это модель для уточнения с пользователями, а не утверждение обязательного юридического маршрута. Каждое направление связывается с конкретным неизменяемым PDF и его редакцией; новая правка создаёт новую редакцию. Статус, время, автор и способ подтверждения фиксируются отдельно от изображения подписи на листе.

## Проверяемость

Для каждого правила хранятся ссылка на источник и результат предметной проверки. Тесты охватывают валидаторы, вычисления и миграции; визуальные примеры проверяют печатный лист. Версия исходных данных сохраняется рядом с экспортом. Перед применением пользователь сверяет схему с фактической геометрией дороги, видимостью, существующими знаками и условиями работ.
