# Предметная сверка перед продолжением и выпуском 0.3.0

Сверено 29.10.2026 по main a5ad72f и результату первой предметной приёмки. Технический этап принят 28.10.2026 по Windows exe №41 на 5e93c0f; [протокол](verification/reports/2026-10-28-technical-regression.md). #110 и #108 приняты и закрыты. #103 возвращён на доработку: исправление из открытого PR #242 ещё не включено в main и не принято на новой сборке. #107 и #109 остаются открытыми. Рабочие источники не публикуются.

## Принятое решение #110 — 25.10.2026

Состав данных утверждён: ширина проезжей части, все значения видимости карточки с различением направлений и объектов, наименование автодороги, км/пк/станция или перегон; интенсивность авт/ч — по нормативным параметрам технического специалиста. Используются карточки, импортированные специалистом. Ежегодное переутверждение — вне ответственности репозитория/разработчика и не условие выпуска ПО. [Текущий контракт](pu66-data.md). Реализация API/сравнения/снимка/листа v11 принята на a5ad72f по PU01–PU12 29.10.2026. Новые изменения требуют соответствующей регрессии; повторного решения о составе данных не требуется.

## Закрытое решение об ответственности за графику

[#111 — права на графику знаков](https://github.com/hhypest/editor-of-tod/issues/111) закрыта по решению владельца проекта 25.10.2026. Обеспечение прав на пользовательскую графику относится к ответственности организации, использующей ПО, и технического специалиста; проверка и обеспечение этих прав находятся вне ответственности репозитория и разработчика. Вопрос исключён из открытых задач и условий выпуска 0.3.0 со стороны проекта. Решение закреплено в [лицензировании](licensing.md#ответственность-за-графику-знаков).

## Как подготовить результаты

1. Для ближайшего зависимого блока выбрать соответствующую строку таблицы и записать конкретные нерешённые вопросы.
2. Подготовить обезличенные примеры для публичных тестов. Рабочие ПУ-66, SQLite, JSON с реальными сведениями, нормативные PDF и рабочие PNG остаются локально.
3. Использовать уже принятые решения #103/#110; завершить только недостающие исходные решения #107, затем реализовать и проверить зависимую техническую часть отдельным PR.
4. Записать предметную приёмку точной сборки. В GitHub публиковать только обезличенный итог, ссылки на задачу и нормативное основание, без исходных файлов.
