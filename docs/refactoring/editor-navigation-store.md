# Навигация и обновление каталогов в Pinia (#191)

Оставшийся исполняемый этап после #231, включённого в main коммитом 9815825. Основа — [ADR-0011](../adr/0011-pinia-ui-state.md) и [карта перехода](pinia-state-plan.md). #191 продолжает интеграцию; ошибочное закрытие исправлено.

## Общие данные

`src/stores/editor-navigation.ts` владеет восемью прежними refs: `activeView`, `projectTab`, `registryTab`, `registriesVisited`, `projectTabChosen`, `helpSection`, `helpOpenKey`, `findingNotice`. Все поля явно возвращаются. `projectTabChosen` относится к общему состоянию: поздний стартовый ответ должен учитывать уже выбранную составителем вкладку.

`App.vue` получает один набор `storeToRefs` и явно передаёт его в `useEditorNavigation`. Совместимый вызов без порта получает store текущего app при создании адаптера. Публичный фасад сохраняет семь refs и шесть команд (13 ключей); внутренний `projectTabChosen` не добавляется в фасад. Читатель получает store без создания ещё одного адаптера.

Тела команд, watcher `placementDirty`, начальная загрузка проектов в `onMounted`, guard выбранной вкладки, DOM focus/scroll, раскрытие details и `nextTick` остаются в прежнем composable. Store не импортирует services, composables, session или DOM и не запускает HTTP/lifecycle. Callback открытия проекта по-прежнему связывает единственную сессию с навигацией в корне. Vue Router не вводится.

`src/stores/catalog-refresh.ts` владеет двумя прежними refs `signCatalogVersion` и `pu66CatalogVersion`. Они общие для SetupWorkspace, RegistryHub, EditorWorkspace и предпросмотра листа. Отдельный store отражает обновление каталогов, а не состояние документа. Корень получает refs и сохраняет прежние increment/reload/invalidate/refresh обработчики и прежние props. Получение store не выполняет invalidation, не перечитывает API и не перемонтирует представления само по себе.

## Почему setup остаётся в корне

`setupOpen`, `setupRegistryStatus`, `setupError` и производный `setupStatus` обслуживают один экземпляр мастера. Корень управляет показом, передаёт ему status через props и показывает локальную ошибку в ProjectHub. Второго владельца или независимого потребителя этих данных нет.

`startupChecked`, `setupRequest` и `sessionStorage` deferred setup остаются рядом с единственным startup/request lifecycle. Перенос этих полей без нового сценария доступа добавил бы глобальное состояние локальному экрану. Локальные файлы, preview, поля и подтверждения SetupWorkspace также не переносятся. Общими являются только счётчики каталогов; их новый владелец описан выше.

## Совместимость и проверка

Форматы JSON v10/SQLite v13, нормативные алгоритмы, белый список #110, лист/PNG, история, recovery и зависимости не меняются. Не добавлены `$reset`, persisted-state plugins, сериализация stores или watchers для синхронизации двух копий данных.

Подготовка прежних navigation tests переведена на отдельную Pinia каждого app; исходные сценарии сохранены. Добавлены сценарии общего чтения без второй загрузки, неизменного фасада, позднего startup response после смены active Pinia, изоляции разных app и пассивного чтения navigation/catalog stores. Эти тесты подготовлены, но в данном шаге **не запускались**.

По уточнению владельца 27.10.2026 окончательные проверки и тестирование состояния, полный check/E2E, итоговый main и Windows exe выполняются после полного погашения технического долга. Они учитываются отдельно от продолжающейся реализации #191. Проверка типов и оформление при подготовке кода не являются итоговой регрессией. Прежний CI #231 не подтверждает этот новый перенос; результат будущих прогонов фиксируется на фактическом коммите/дереве.
