# Чтение ПУ-66 и разрешение ключей (#135)

`server/pu66/repository.ts` владеет `list/getScheme/getNorms`, SQL проекций и преобразованием строк SQLite. `server/pu66/key-resolver.ts` владеет прежним разрешением ключа. Это первая часть выделения модуля ПУ-66 по [ADR-0010](../adr/0010-modular-server-persistence.md), [дальнейшие шаги](server-god-object-plan.md) остаются открытыми.

## Сохранённые правила чтения

- Если текущая карточка с запрошенным ключом существует, она имеет приоритет над таблицей aliases. Иначе используется одна записанная связь; отсутствие связи даёт `null`, `new_key = NULL` — прежний `AmbiguousPu66Key`. Цепочки не обходятся, потерянные цели не исправляются автоматически; проекция отсутствующей цели даёт `null`.
- Выборка схемы остаётся прежней: referenceId, location/axisLabel, roadName, crossingWidthMetres/crossingRoadLengthMetres и metadata версии/даты. XLSX, персонал и техническая таблица в неё не попадают. Значения ячеек не преобразуются в новые нормативные выводы.
- Локальный список дополнительно содержит section/station/carCountPerDay и текущую сверку. Нормативная выборка остаётся отдельной: категория дороги, интенсивность за сутки, видимость поезда, годы и технические строки без исходных координат строк XLSX.
- Сверка в списке выбирается только для текущей редакции карточки, по verified_at DESC и затем id DESC. Сверка старой редакции не становится отметкой новой.
- Обычный список исключает карточки по последнему lifecycle id, `includeExcluded` сохраняет полный список; порядок — по ключу. Прямые проекции не добавляют запрет по lifecycle: прежняя проверка допустимости новой привязки остаётся в HTTP/прикладном сценарии.

Все проекции используют прежние функции `server/pu66.ts` без расширения белого списка. Состав полей #110 уже утверждён, но его дальнейшая реализация остаётся после полного технического этапа. Смена реестра не переписывает исторические снимки проекта.

## Зависимости и совместимость

Оба владельца получают существующее соединение; они не открывают/закрывают базу, не мигрируют, не запрашивают часы и не начинают транзакции. Читатель получает узкий `resolve` вместо RegistryStore. Фасад делегирует три прежних метода; status/lifecycle/verification используют тот же resolver на том же соединении внутри прежних команд.

`AmbiguousPu66Key` находится в `server/pu66/errors.ts`, старый экспорт фасада указывает на **тот же конструктор и сообщение**. URL/body/status, текущие ограничения полей, JSON v10/SQLite v13, импорт и нормативные алгоритмы сохраняются.

## Проверки и следующий шаг

- [Два контракта фасада](../../server/__tests__/pu66-read-contracts.test.ts) сначала прошли до переноса: приоритет ключей/ошибки/белые списки и metadata сверок/исключение.
- [Прямые проверки](../../server/__tests__/pu66-repository.test.ts) используют вымышленную persisted SQLite без RegistryStore: read-only соединение, alias/null/chain/dangling, точные поля и типы, сверка текущей редакции, latest-id lifecycle, обновление через второе соединение без изменения старой редакции.
- Прежние imports/API/lifecycle/frozen JSON и SQLite тесты сохраняются, включая миграцию станционных ключей, отказ неоднозначной привязки и запрет новой привязки исключённой карточки.

Далее — выделение сверок (`Pu66VerificationRepository`), затем lifecycle/import. Чтение является частью модуля ПУ-66, а не отдельной базой или новым bounded context. #135/А4 открыты; Pinia первой после А4, весь технический этап до новых функций.
