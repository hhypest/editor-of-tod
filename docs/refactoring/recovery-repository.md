# Атомарные команды копий восстановления (#135)

`server/recovery/recovery-repository.ts` владеет SQL recovery, преобразованием строк и командами `list/get/claim/renew/release/save/delete`. Реализует границу из [ADR-0010](../adr/0010-modular-server-persistence.md); [общий план](server-god-object-plan.md) остаётся открытым.

## Граница записи

Раньше HTTP PUT отдельно вызывал проверку владельца, восстановление исходника и запись; только последняя часть начинала транзакцию. Теперь маршрут передаёт одну команду. `save` выполняет под одной `BEGIN IMMEDIATE`:

1. Прежнюю проверку активного владельца и восстановление полного Scheme. SHA разрешает повторно использовать только исходник **этой же** копии; чужая ссылка, новая копия со ссылкой и одновременный inline/sourceSha отклоняются.
2. Проверку 32 МБ по полному восстановленному UTF-8 JSON, включая неприменённый ввод. Маленький SHA-запрос не обходит лимит.
3. Прежние проверки записанного владельца и expectedVersion, source/dedup и запись снимка с продлением аренды.
4. COMMIT либо ROLLBACK всей операции при ошибке. Исходник не остаётся сиротой, а owner/lease/version и неприменённые поля не обновляются частично.

SQL записи и прежний порядок отказов сохранены; область блокировки расширена на чтение/восстановление исходника, как требует ADR. Чужой активный владелец проверяется до разбора Scheme. Истечение аренды не разрешает другому окну записать копию без claim. Возобновление старого владельца после takeover отклоняется и после release новым владельцем.

`claim` и `delete` сохраняют прежние `BEGIN IMMEDIATE`. `renew/release` остаются одиночными UPDATE: продление не меняет снимок/версию, запоздалый release другого владельца ничего не освобождает. Удаление включает [очистку последней ссылки](project-source-store.md) в ту же транзакцию; проектные редакции не создаются.

## Совместимость и зависимости

Одна SQLite/соединение, lease 120 с, heartbeat 20 с, JSON v10/SQLite v13, URL/body/status и короткие receipt сохранены. Состав и формат неприменённых полей не меняются. Приёмка настоящего сна #134 остаётся принятой; клиентская очередь и generation fence не переписываются.

Репозиторий получает готовое соединение, узкие операции source и функцию часов; не открывает/закрывает базу, не мигрирует и не знает HTTP/Vue. RegistryStore временно делегирует прежние методы и сохраняет receiver часов. `RecoveryOwned` перенесён в `storage-errors.ts`, старый экспорт фасада указывает на тот же конструктор и сообщение.

Совместимые read guard/resolver пока доступны через фасад; это не разрешение на запись и не последовательность для HTTP. PUT больше их не вызывает отдельно. Удаление forwarding helpers производится вместе с переводом оставшихся вызывающих по общему плану.

## Проверки и следующий шаг

- [Контракты фасада](../../server/__tests__/recovery-repository-contracts.test.ts) сначала прошли до переноса: receiver часов, pending input/lease/claim и rollback обновления при отказе SQLite trigger.
- [Прямые тесты](../../server/__tests__/recovery-repository.test.ts) проверяют owner/version/source, cleanup и полный UTF-8 размер. Во время source decode второе соединение пытается claim истёкшей копии и получает SQLite lock; после успешной записи новый claim отклоняется владельцем. Busy timeout 1 мс задаётся только тестовому второму соединению, настройки программы не меняются.
- [HTTP-контракт](../../server/__tests__/recovery-api-contracts.test.ts) фиксирует порядок 409/400, изоляцию исходника, отсутствие записей при отказе и прежний receipt. Прежние ownership/wake/queue, source failure/cleanup, frozen JSON/SQLite, API и E2E сохраняются.

Проекты, recovery, [ручные реестры](legacy-registry-repository.md) и [чтение/ключи ПУ-66](pu66-read-repository.md) выделены. Далее — сверки ПУ-66 и остальные области хранения/маршруты. #135/А4 остаются открытыми; Pinia первой после А4, весь технический этап до новых функций.
