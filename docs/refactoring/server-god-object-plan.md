# План разделения серверного хранения и HTTP (#135)

Сверено 25.10.2026. Основа — предоставленные владельцем ADR-0010 и план серверного рефакторинга; последовательность ниже привязана к текущим задачам. Это план реализации, а не отчёт о выполненном переносе. Подробные интерфейсы в исходном предложении считаются эскизами: перед каждым PR их сверяют с фактическим кодом.

[ADR-0010](../adr/0010-modular-server-persistence.md) · [Архитектура](../architecture.md) · [ROADMAP](../../ROADMAP.md) · [#135](https://github.com/hhypest/editor-of-tod/issues/135)

## Вход и порядок

1. #136 завершена: клиентский фасад и независимые адаптеры существуют.
2. #134 завершена: приёмка 25.10.2026 — 10/10, настоящий сон Windows проверен. Серверный этап разблокирован. Исходное требование: отдельное исправление recovery после сна. До переноса recovery SQL фиксируются проверки истёкшей аренды, wake/claim/save, поздних ответов и сети; настоящий сон Windows проверяется отдельным протоколом.
3. Выполняются небольшие совместимые PR #135 в порядке ниже.
4. Завершение архитектурного А4 фиксируется после разделения оболочки/сессии и серверных границ, сохранения контрактов и проверки Windows exe.
5. Первая следующая задача — интеграция Pinia #191 по решению владельца. Затем #184, #137, #138 и итоговая регрессия; новые функции 0.3.0 начинаются только после полного технического этапа. А4 и интерфейсный И4 — разные этапы. Pinia не внедряется посреди исправления recovery или переноса SQL.

## Инварианты каждого переноса

- Одна SQLite и единый жизненный цикл соединения; прежние транзакции и атомарные проверки владельца/версии.
- JSON v10, SQLite v13, старые читатели, исторические редакции и исходный JSON по SHA-256.
- HTTP URL, методы, query/body, коды/тексты ошибок, заголовки, ETag и ограничения Host/Origin.
- Неизменяемые исторические PNG и снимки ПУ-66; подтверждения сохраняют источник и цитату.
- Миграционная копия до изменений; ошибка копии блокирует миграцию. Специальный v2 и VACUUM вне транзакции сохраняются.
- При конфликте не теряются ввод, история и черновики; запоздалый ответ не означает «сохранено».
- Нормативные алгоритмы, SVG, печать и PNG не меняются в структурных PR.

ORM, микросервисы, несколько баз, DI-фреймворк и новые форматы не входят. Разделение по таблицам само по себе не создаёт bounded contexts.

| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Проекты   | Создание, новая редакция, no-op, forceRevision, expectedRevision, возврат как новая редакция, размер, legacy source/SHA, повреждённая/удалённая ссылка |
| Recovery  | Создание/повтор, версия, claim/renew/release/delete, чужой владелец, expiry, wake/claim/save, source и очистка последней ссылки                        |

### 2. Инфраструктура базы

Отдельными PR: подключение/закрытие → migration backup → runner и последовательные миграции → ручной backup. Публичный `RegistryStore` пока сохраняется.

Подключение владеет каталогом/файлом/правами, настройками DatabaseSync, foreign_keys и закрытием при ошибке. Migration runner не прячет v2/VACUUM в общий wrapper. Проверяется каждая поддерживаемая исходная версия; новая база, v13/no-op и будущая версия — отдельные случаи. Данные fixtures вымышленные; бинарные базы создаются из хранимого тестового представления, рабочие SQLite не коммитятся.

### 3. Источники, проекты и recovery

`ProjectSourceStore` владеет encode/decode по SHA, восстановлением самодостаточной схемы и удалением только после последней ссылки. `ProjectRepository` атомарно выполняет source + draft + revision, сохраняет no-op/forceRevision и возврат новой редакцией.

`RecoveryRepository` предоставляет команды list/get/claim/renew/release/save/delete. Внутри одной `BEGIN IMMEDIATE` save проверяет owner/version, разрешает source, записывает снимок и продлевает аренду. Маршрут больше не собирает команду из assert → resolve → save. Перенос сохраняет уже проверенное поведение #134.

### 4. Legacy и ПУ-66

Legacy crossings/normative/revisions выделены; начальное наполнение остаётся отдельной операцией инициализации. Чтение ПУ-66, key resolver, журнал сверок, lifecycle и импорт repository/service выделены. Сервис lifecycle получает узкие запросы и синхронный TransactionRunner, повторно проверяет полный план под блокировкой после backup. Карточки, редакции, aliases, lifecycle и сверки остаются одной предметной областью.

Preview/apply используют общий расчёт плана. Импорт, sources, текущие карточки, редакции и restore events остаются одной транзакцией; проекты и исторические ключи автоматически не заменяются.

### 5. Документы, подтверждения и знаки

Документы/amendments выделены в repository/service: SQL/row mapper, schema/SHA/amends проверки и узкий запрос ссылок из истории знаков; одиночные INSERT/UPDATE и прежний порядок отказов сохранены. Текст страниц/подтверждения выделены в отдельные repositories, нормативные сценарии получают узкие операции вместо RegistryStore; тела SQL/транзакций/алгоритмов сохранены. После [отдельного исправления #215/#216](document-deletion-atomicity.md) выделен [DeleteNormativeDocument](delete-normative-document.md): прежняя атомарная команда и узкие владельцы DELETE/count ссылок, без SQL в фасаде удаления. SignCatalogDocumentReferences обслуживает также запрет смены kind. [Каталог знаков](sign-catalog.md) выделен с прежними plan/import/latest/list/PNG/history и узкими ZIP/PDF операциями. Выделен [ручной composition root](composition-root.md); далее транспорт. Удаление проверяет ссылки из amendments, партий знаков и подтверждений в одной транзакции. Batch/active/history знаков сохраняют прежние границы атомарности; historical asset не подменяется active PNG.

### 6. Composition root и транспорт

[Ручной composition root](composition-root.md) выделен: создаёт конкретные SQLite-адаптеры на одном соединении, выполняет прежнюю миграцию/seed и закрытие при отказе. RegistryStore пока сохраняет API и lifecycle после успешной сборки. Route groups получают узкие зависимости; application services не знают HTTP. Общий транспорт владеет JSON/body limits, security, path parsing, error mapping, бинарными ответами и static files.

Порядок: HTTP-примитивы → project/recovery routes → ПУ-66 → signs/documents → system/diagnostics/legacy → тонкий bootstrap/shutdown. `server/index.ts` после перехода не содержит SQL или предметные таблицы.

### 7. Удаление совместимого фасада

Forwarding method удаляется только после прямых тестов нового контракта, перевода всех вызывающих и поиска оставшихся обращений. Финальный фасад удаляется или заменяется небольшим владельцем lifecycle базы с `close()`/metadata. Временный фасад не получает новые предметные сценарии.

## Проверки и критерии выхода

Каждый структурный PR: `npm run check`, полный E2E, существующие frozen JSON/SQLite и API/конкурентные тесты. Если перенос затрагивает базу, дополнительно проверяется соответствующая матрица миграций/backup; Windows lifecycle и exe — Windows CI и рабочий протокол. Каждый PR имеет собственную точку отката без миграции пользовательских данных.
