# Ручные реестры и история (#135)

`server/legacy/legacy-registry-repository.ts` владеет ручными `crossings/normative` и общей для них историей `revisions`. Это совместимая часть локального API, отдельная от импортированных карточек ПУ-66, библиотеки PDF и подтверждаемых нормативных параметров. [ADR-0010](../adr/0010-modular-server-persistence.md) · [серверный план](server-god-object-plan.md).

## Сохранённый контракт

- Прежние Zod-схемы проверяют и нормализуют draft до `BEGIN IMMEDIATE`: даты, длины, обязательные поля, дата/ответственный у проверенной нормативной записи. Невалидный ввод не начинает и не откатывает чужую транзакцию.
- В одной прежней транзакции проверяется `expectedRevision`, обновляется текущая запись и добавляется история. Ошибка поздней записи истории откатывает и текущую запись; соединение остаётся пригодным к повтору.
- Каждое успешное сохранение, включая одинаковое содержимое, создаёт новую версию. Проектная оптимизация no-op сюда не переносится.
- Реестры сортируются по ключу, история — по возрастанию версии. Одинаковый ключ в двух видах реестра не смешивает их историю.
- Текущие записи валидируются при чтении. Исторический payload остаётся `unknown`: JSON разбирается как записан, без схемы текущего draft и без обновления байтов SQLite.

Репозиторий получает существующее соединение и функцию часов. Он не открывает/закрывает базу, не мигрирует её и не заполняет начальными данными. RegistryStore делегирует пять прежних публичных методов; замыкание сохраняет прежний receiver часов. Ошибка конфликта использует тот же конструктор из `storage-errors.ts` и прежний экспорт фасада.

## Начальное наполнение

Четыре прежние записи находятся в `server/legacy/initial-normative-entries.ts`; тексты, ссылки, статусы и порядок не меняются. Условие и цикл инициализации остаются отдельно в фасаде после миграций: записи добавляются только при пустом нормативном реестре. Непустой пользовательский реестр не дополняется до набора defaults; повторное открытие не меняет его версии или историю.

Это не новая редакция нормативных правил и не перенос миграций в предметный репозиторий. Изменения оснований/значений и состава данных ПУ-66 сюда не входят.

## Проверки и следующий шаг

[Предварительные контракты фасада](../../server/__tests__/legacy-registry-contracts.test.ts) прошли до переноса: seed/receiver/reopen и rollback для обоих реестров при отказе SQLite trigger. [Прямые тесты](../../server/__tests__/legacy-registry-repository.test.ts) фиксируют нормализацию, разделение видов, запись без no-op, порядок/совместимость истории, конфликт двух соединений, ошибки валидации/часов и отказ невалидной текущей записи без её перезаписи.

Прежние store/API, frozen JSON/SQLite, backup и браузерные проверки сохраняются. Одна SQLite, SQL/транзакции, JSON v10/SQLite v13, HTTP и нормативные алгоритмы не меняются.
