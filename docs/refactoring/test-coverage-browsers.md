## Компоненты

В дополнение к существующим store-consumers и mounted composable-тестам добавлены восемь сценариев настоящих SFC `SchemeReview`/`DiagnosticsPanel`. Vue client renderer сохраняет дерево, текст, свойства и обработчики; браузерные DOM/layout-свойства остаются в Playwright. Предметные `reviewScheme`, `setMark`, `markState` и импорт не подменяются; адаптер ПУ-66 и HTTP-диагностика заменены управляемыми ответами.

Проверяются emit неизменённого исходного/нового проекта и отрисовка принятой/устаревшей отметки, disabled + event guard для locked/pending, причина blocked и точная navigate-находка; ошибка/повтор чтения журнала, busy до окончания очистки, отсутствие ложного успеха после отказа и безопасная выгрузка формы проекта без его текстов/ключа переезда с освобождением Blob URL.

Отдельный контракт импортирует **все настоящие SFC** как client modules без app/active Pinia/HTTP. Это также обеспечивает честный знаменатель V8 coverage: подменённые в других тестах формы иначе получали ноль измеренных строк. Summary отклоняет такой отчёт; непроверенные функции/setup остаются в знаменателе, а не исчезают из покрытия.

## Покрытие в CI

`npm run test:coverage` запускает прежний Vitest-набор с V8. В Ubuntu validate тот же `npm run check` включает coverage через `TOD_TEST_COVERAGE=1`; повторного unit-прогона ради отчёта нет. Windows сохраняет прежний одиночный worker CI и те же timeout/assertions.

Включены production TS/Vue из src и TS из server, в том числе непосещённые файлы. Исключены тестовые каталоги, d.ts и сгенерированный список файлов диагностики. HTML, LCOV и JSON summary загружаются как `coverage-<run_id>` на 14 дней; таблица lines/statements/functions/branches видна в Actions Summary. Отчёт формируется также при тестовом отказе. Числовой процентный порог произвольно не назначается: это измерение, а не доказательство предметной корректности.

Локальная проверка инфраструктуры: **140 файлов / 1101 тестов**, прежние тесты сохранены. Lines 66,07%, statements 65,35%, functions 54,50%, branches 52,94%; нулевых по измеренным строкам SFC нет. Это результат тестового набора данного дерева, без браузерного покрытия и без заявления об итоговой приёмке состояния.

Прямая devDependency `@vitest/coverage-v8` 5.0.5 совпадает с Vitest, лицензия MIT. Десять новых узлов lockfile имеют MIT; тексты лицензий проверены в пакетах (в том числе LICENCE у tinyrainbow). Старые версии/integrity и платформенные libc metadata сохранены. Состав runtime-зависимостей и проверка лицензий программы не меняются.

## Два браузера и диагностика отказов

Команда `npm run test:e2e` последовательно выполняет все **56 сценариев в Chromium и 56 в Firefox** в отдельных процессах Playwright. Каждый процесс запускает собственный сервер со свежей временной SQLite; результаты разнесены в test-results/chromium и test-results/firefox. Набор одного браузера: `npm run test:e2e -- --project=firefox`. Прямой Playwright по умолчанию запускает Chromium, допускает явный одиночный --project; для двух браузеров используется общий runner. Четыре теста runner фиксируют отдельные процессы/env/output, передачу фильтров, отказ неизвестного проекта и сохранение неуспешного статуса первого браузера после успешного второго. `npm run test:e2e -- --list` показывает два набора по 56 сценариев. Установка: `npx playwright install --with-deps chromium firefox`. Обычный CI и ручной Windows exe workflow устанавливают оба браузера. Запуск exe остаётся исключительно ручным.

Печатный сценарий создаёт учебный проект с одной стойкой 1.25 и загружает программно нарисованный PNG из синтетического каталога; перед print media проверяет отсутствие blockers. Исходная legacy-фикстура с неизвестным 9.99 сохраняется для прежних импортных тестов. Сценарий в обоих браузерах проверяет print media, отступ, видимость контейнера и SVG. Прежний вызов `page.pdf` и проверка ровно одной страницы сохраняются в Chromium: API генерации PDF Firefox не предоставляет. Пропуска всего сценария или ослабления исходного PDF-ожидания нет.

Прежние workers=1, retries (CI 2 / локально 0), timeout/hook limits и предметные ожидания не меняются. При отказе сохраняются trace, screenshot и JSON requestfailed (browser, время, метод, pathname, error; без body/query), включая сценарии первоначальной настройки. CI выгружает весь test-results на 7 дней. `ERR_NO_BUFFER_SPACE` по-прежнему отличается от предметного отказа: один успешный повтор не объявляется исправлением его причины.

Локальный Firefox установлен, но три выбранных сценария остановились на создании страницы **до загрузки приложения**. Минимальная проверка Firefox с пустой страницей воспроизвела `Target crashed`; stderr сообщает `Sandbox: writing /proc/self/uid_map: EPERM`. Настройки sandbox/ожидания не ослаблялись. Загрузка Chromium в данной среде завершилась ошибкой сервера (повреждённый ZIP / HTTP 400). Поэтому прохождение браузерного набора здесь не заявляется; обязательное подтверждение 112 сценариев — в CI PR. Отдельная итоговая регрессия main и Windows exe остаётся после включения технической очереди.

После первого review #236 исправлены оба P1: общая база между браузерами заменена отдельными процессами/серверами/SQLite, печатная проверка получает полностью подготовленный учебный лист, а не скрытый из-за отсутствующего знака SVG. Ожидания plan.added === 1 и ровно одной страницы PDF сохранены.
