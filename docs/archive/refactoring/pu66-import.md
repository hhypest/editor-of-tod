`server/pu66/import-repository.ts` владеет inspection по текущему ключу и SQL источников, текущих карточек и неизменяемых редакций. `server/pu66/import-service.ts` рассчитывает counts/preview/fingerprint и координирует запись с явным возвратом исключённых карточек. Это продолжение [lifecycle](pu66-lifecycle.md) и [ADR-0010](../../adr/0010-modular-server-persistence.md), без нового сценария или формата данных.

## Сохранённое поведение

- Inspection сохраняет входной порядок, порядок свойств JSON, отказ повторного ключа и выбор add/update/unchanged по SHA исходной книги. Текущая карточка ищется по переданному ключу без автоматической подмены alias; статус использует существующий resolver. Preview скрывает исходники, SHA и техническую таблицу, но SHA и полный статус участвуют в прежнем fingerprint.
- `planPu66` и прямой import возвращают прежние три счётчика. Неизменённый SHA не создаёт источник, новую редакцию, новое время или обновлённое имя книги. Изменённая карточка сохраняется в current и history с одним временем; время получается отдельно для каждой изменённой карточки. Первый источник с данным SHA остаётся прежним, имя в хранилище ограничено 240 символами.
- Обычный импорт, включая CLI, не возвращает исключённую карточку автоматически. Явный возврат допускается только для исключённых карточек из пакета. Под `BEGIN IMMEDIATE` сначала проверяется присутствие ключей, затем прежний lifecycle plan; после записи карточек события возврата ссылаются на их новые редакции. Неизменённую карточку можно явно вернуть без новой редакции.
- Вставка restore events перенесена в `Pu66LifecycleRepository.appendImportRestores`. Её прежний INSERT SELECT и отдельный вызов часов для каждого ключа сохраняются; общий timestamp обычного lifecycle batch здесь не применяется. Прямой import проверяет нормализованный lifecycle plan, но записывает прежние поля исходной restoration; HTTP заранее нормализует body.
- Источники, current, revisions и все restore events входят в одну транзакцию. Ошибка SQL, часов или любого события откатывает весь пакет. Другие соединения не могут писать во время проверки возврата и записи; до commit они видят прежнее состояние.

## Зависимости и транспорт

Repository получает существующее соединение, узкий запрос статуса и часы; не открывает/закрывает базу и не запускает миграции или backup. Сервис получает узкие inspect/write, lifecycle plan, appendImportRestores и синхронный TransactionRunner; не импортирует RegistryStore, DatabaseSync или HTTP. Фасад сохраняет прежние inspect/plan/import и делегирует существующий preview через `planPu66Import`.

`pu66-web-import.ts` получает узкие команды preview/import/backup. Схемы body, разбор XLSX, base64, лимиты и статусы ошибок остаются прежними. Порядок apply сохранён: preview/сравнение fingerprint → no-op без backup либо асинхронный backup → повторный preview/сравнение → синхронная команда import. Полный fingerprint проверяется до команды, как и раньше; внутри транзакции повторяется проверка допустимости возврата. Этот перенос не добавляет fingerprint-проверку под блокировкой. Конструктор InvalidPu66Upload перенесён в общий модуль ошибок с прежним экспортом и status.

## Проверки и продолжение

Три [контракта фасада](../../../server/__tests__/pu66-import-contracts.test.ts) предварительно прошли до переноса: порядок inspection/дубликаты/no-op/receiver часов, полный откат при отказе второго возврата и порядок проверки restoration. [Прямые проверки](../../../server/__tests__/pu66-import-service.test.ts) используют вымышленную SQLite без RegistryStore: read-only/aliases, bytes/SHA dedup/immutable history, whitelist/fingerprint/ошибки, rollback редакции/события/часов, блокировка второго соединения, отдельные timestamps и узкий backup port. Сохраняются существующие imports/web/lifecycle/API, frozen JSON/SQLite и полный E2E.

Fingerprint вымышленного preview дополнительно сверяется с фиксированным результатом исходного planImport на b1d7bfc. SQL перенесён без изменения строковых литералов; тело расчёта preview, порядок JSON и hash совпадают после замены зависимостей. JSON v10/SQLite v13, белые списки #110, нормативные алгоритмы, лист и ответственность за переутверждение карточек сохраняются. Новых зависимостей нет.
