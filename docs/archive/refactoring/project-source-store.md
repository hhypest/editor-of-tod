`server/projects/project-source-store.ts` владеет только SQLite-представлением исходного JSON. Это часть серверного переноса по [ADR-0010](../../adr/0010-modular-server-persistence.md), а не новый формат проекта. [Следующие шаги](server-god-object-plan.md).

## Ответственность

- `encode(scheme)` оставляет созданный в редакторе проект обычным JSON. У импортированного проекта исходные UTF-8 байты хранятся один раз в `project_sources` по SHA-256; снимок SQLite содержит `originalJsonSha256`.
- `decode(payload)` читает прежние inline-снимки через существующий версионируемый reader. Для ссылки проверяет форму SHA, наличие исходника и совпадение его хеша, возвращая самодостаточный `Scheme` с `originalJson`. Внешний JSON/API не получает внутреннюю ссылку SQLite.
- `removeUnreferenced(payload)` после удаления ссылки проверяет текущие проекты, все исторические редакции и recovery. Исходник удаляется только при отсутствии ссылок во всех трёх таблицах. Другие исходники не затрагиваются; глобальная фоновая очистка не вводится.

Модуль получает **то же соединение**, которое открыл RegistryStore. Он не открывает/закрывает базу, не выполняет миграции, не владеет временем и не начинает/завершает транзакцию. Source + draft + revision и удаление recovery + cleanup остаются внутри прежних `BEGIN IMMEDIATE` фасада. Отказ поздней записи или очистки откатывает всю операцию.

Проверка owner/version и ограничение повторного использования исходника текущей recovery выполняются в атомарной команде [RecoveryRepository](recovery-repository.md). `ProjectSourceStore` не является разрешением выдавать любой исходник по произвольному SHA через HTTP.

## Проверки

- [Прямые тесты](../../../server/__tests__/project-source-store.test.ts): native без таблиц/миграции; frozen inline v6; точные UTF-8 байты и dedup; malformed/missing/corrupted SHA; сохранение ссылок из каждой из трёх таблиц и удаление последней; rollback на том же соединении.
- [Контракты фасада](../../../server/__tests__/project-source-contracts.test.ts) сначала прошли на исходном RegistryStore до переноса. SQLite triggers моделируют отказ записи исторической редакции и отказ удаления исходника; проект/источник/recovery остаются согласованными, повтор после устранения отказа успешен.
- Прежние store/API, recovery ownership и frozen JSON/SQLite проверки сохраняются. SQL, тексты ошибок, JSON v10/SQLite v13, лимиты, lease и HTTP-контракты не меняются.

Выделение источников завершено; проекты и история перенесены в [ProjectRepository](project-repository.md), восстановление — в [RecoveryRepository](recovery-repository.md). Остальные области хранения, прикладные операции, composition root и route groups ещё предстоят. #135 и архитектурный А4 остаются открытыми; после А4 первой идёт Pinia #191, затем остальной технический этап до функций 0.3.0.
