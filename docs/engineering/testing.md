# Как выполнять проверки

Тип: действующая инструкция для разработчика и проверяющего. Сверено 30.10.2026 по package.json и workflows на реализации main a5ad72f; документальная основа — 65826e5. [Текущая предметная сверка 0.3.0](../verification/0.3.0/README.md) · [Ручные чек-листы](../../TESTING.MD) · [Выпуск](../verification/release.md).

## Подготовка и общий check

Используйте Node/npm согласно [разработке](../development.md) и [матрице платформ](../platforms.md). После первой установки зависимостей выполните из корня репозитория:

```bash
npm ci
npm run check
```

Check последовательно проверяет актуальность диагностического перечня файлов, архитектурные зависимости, документацию, публичные файлы, форматирование, Oxlint/ESLint, типы, прямой запуск Node entrypoints, Vitest и production build. Ожидается код завершения 0. Точный состав задаёт [package.json](../../package.json), а не число тестов из старого протокола. Проверка лицензий входит в сборку. CI дополнительно собирает coverage; покрытие и успешный check не удостоверяют предметную применимость схемы.

Для отдельного сбоя используйте соответствующую команду, например `npm run check:runtime`, `npm run test` или `npm run test:coverage`. После исправления выполняется полный check. Исторические эталоны и ожидания не обновляют для сокрытия ошибки переноса.

## Браузерные сценарии

```bash
npx playwright install chromium firefox
npm run test:e2e
```

[Runner](../../scripts/test-e2e.ts) по умолчанию запускает Chromium и Firefox раздельно, с отдельными процессами и временными SQLite. Рабочая база не используется. Для одного браузера: `npm run test:e2e -- --project=chromium` или `--project=firefox`. Тестовые данные вымышленные. Ошибка установки или запуска браузера записывается как невыполненная проверка, а не успешный результат.

Воспроизводите проблему на точном коммите и проекте браузера. Сценарий должен работать без данных от предыдущего теста; вывод с повторной попыткой и flaky фиксируется в протоколе. Список сценариев — в [tests/e2e](../../tests/e2e). При проверке собранного клиента `npm run preview` запускает API и просмотр на 4173; `npm run local` обслуживает собранное приложение через один адрес, обычно 4100. Подготовка сборки — `npm run build`.

## Windows exe и рабочее место

Сборка exe запускается отдельно вручную по [процессу выпуска](../verification/release.md). Для существующего тестового файла задайте `TOD_E2E_EXE` и выполните тот же E2E runner. Пример PowerShell, путь замените на свой тестовый файл:

```powershell
$env:TOD_E2E_EXE = 'release\editor-of-tod.exe'
npm run test:e2e
Remove-Item Env:TOD_E2E_EXE
```

E2E использует временную SQLite. Проверка Windows Node CI не заменяет запуск готового exe, браузерный прогон не заменяет сон/пробуждение и фактическую печать на рабочем месте. Используйте отдельную тестовую папку и базу, сохраните резервную копию. Возврат базы проверяйте при остановленной программе с сохранением заменяемого файла.

## Что приложить к результату

Укажите дату, версию, полный SHA, PR/ветку или тег, номер сборки exe и ссылку на CI. Отдельно перечислите автоматические проверки, ручные сценарии, неприменимые/невыполненные пункты и решение специалиста. При сбое запишите минимальные шаги, ожидание и результат; не публикуйте рабочие карточки, SQLite, PDF стандартов или конфиденциальные листы.

Заполненный результат добавляется в [verification/reports](../catalog.md#протоколы-конкретных-проверок), текущий статус — в индекс версии и issue. Шаблон записи:

| Поле                 | Заполняемое значение                                                 |
| -------------------- | -------------------------------------------------------------------- |
| Срез                 | Дата, версия, полный SHA, тег/PR, сборка exe                         |
| Среда                | ОС, браузер, сведения о тестовой базе                                |
| Автоматика           | Команды, итог, повторы/ограничения и ссылки                          |
| Ручная проверка      | ID сценария, ожидание, факт, принято/ошибка/не проверено/неприменимо |
| Решение              | Кто подтвердил результат и что именно принято                        |
| Локальные приложения | Где хранятся рабочие материалы; публично — только обезличенный итог  |

Датированные результаты из прежнего TESTING сохранены в [архиве](../archive/testing-before-2026-10-30.md). Они не назначают количество тестов, номер следующей версии или текущую очередь.

## Автоматическая проверка документации

`npm run check:docs` входит в общий check. Для отдельного машинного отчёта: `node scripts/check-documentation.ts --json`. Скрипт читает только файлы репозитория и ничего не меняет; внешние сайты и пользовательские каталоги не обходит.

Проверяются обычные локальные ссылки и якоря (включая кириллицу, повторные заголовки и reference-ссылки), наличие каждого Markdown-файла в таблицах каталога и его счётчик, тип/статус активного документа, дата/точный исходный SHA архива, существование указанных текущих путей кода и npm-команд. Установка Chromium/Firefox сверяется с обоими workflows. Кодовые блоки не создают заголовки или Markdown-переходы.

Исторические форматы, команды и прежние пути в archive/, датированных протоколах и исходном контексте ADR не объявляются ошибкой текущей инструкции. Для текущей карты диагностики есть одно узкое исключение: server/store.ts — имя старого кадра, сохранённое для чтения прежних событий; другие несуществующие текущие пути отклоняются. Числа форматов дополнительно защищает прежний docs-versions.test.ts.

Проверка не доказывает истинность предметного правила, доступность внешнего URL или факт приёмки. При переносе документа обновляйте основной путь, входящие ссылки и каталог одним изменением; не скрывайте ошибку перемещением действующей инструкции в архив.
