# Подготовка данных ПУ-66 для будущего каталога

**Статус: проект порядка массовой загрузки и сверки.** Ответственным за актуализацию и составление реестра ПУ-66 определено линейное подразделение ОАО «РЖД». Карточки конфиденциальны: они не публикуются в GitHub и предоставляются только организациям, участвующим в согласовании и утверждении. В приложении есть локальный SQLite-реестр для ручного ввода, но массовой загрузки пока нет. Ссылка на переезд из старого JSON переносится как `crossing.referenceId`, а `crossing.snapshot` остаётся `null`; совпадение с локальным реестром пока не создаёт подтверждённую карточку в схеме.

## Перед получением данных

1. Зафиксировать подразделение-владельца каталога, источник карточек, дату их состояния, территорию охвата, порядок получения изменений и уполномоченного на сверку специалиста.
2. Установить состав полей для локального хранения и передачи согласующим организациям по принятому порядку. Реальные карточки, встроенные 73 записи старого HTML и сканы в GitHub не добавляются.
3. Согласовать минимальный состав полей для схемы: устойчивый идентификатор переезда, проверенные характеристики, важные для выбора варианта и размещения элементов, ссылка на источник, версия записи и дата сверки. Персональные данные и реквизиты, не необходимые для составления схемы, исключить из каталога.

## Сейчас реализовано локально

- `private-data/registry.sqlite` создаётся на компьютере составителя, исключён из Git и доступен приложению только через процесс на `127.0.0.1`.
- Можно вручную внести ключ, место, автомобильную дорогу, владельца, реквизиты и дату карточки, дату сверки и примечание. Исправление создаёт новую редакцию записи; устаревшая правка отклоняется.
- Резервная копия SQLite создаётся по кнопке в `private-data/backups/`. База не шифруется приложением; доступ контролирует операционная система и правила хранения организации.
- JSON-проект из старого редактора не заносится в реестр автоматически; само наличие ключа не означает сверку карточки.

## Предлагаемый порядок массовой загрузки

1. Получить разрешённую выгрузку от владельца данных и сохранить оригинал отдельно от приложения с установленным доступом. Для разработки и CI использовать только вымышленные примеры `TEST-001`, `TEST-002` и другие обезличенные фикстуры.
2. Описать схему входного файла и таблицу соответствия полей ПУ-66 модели приложения. Явно указать единицы измерения, обязательность, допустимые значения, способ указания отсутствующих сведений и правила нормализации идентификаторов.
3. Проверить каждую запись на дубликаты, пропущенные поля, неоднозначные идентификаторы, неверные единицы и устаревшую дату сверки. Ошибки представить на просмотр ответственному, не исправлять их автоматически без следа.
4. Перед применением показать число новых, изменённых и исключённых записей. Специалист сверяет выборку с оригиналами и подтверждает версию каталога. Хранить дату, источник, версию и результат сверки для последующего аудита.
5. Не переписывать данные уже сохранённой схемы при обновлении каталога. Для новых и изменяемых проектов предусмотреть явный выбор обновлённой записи с просмотром отличий; прежнюю версию каталога сохранять для воспроизведения документа.
6. Проверить импорт на обезличенных сценариях: корректный переезд, отсутствующий идентификатор, конфликт дубликатов, изменение владельца дороги и исправление характеристики. Затем проверить ограничения доступа и восстановление предыдущей версии каталога.

## Решения перед реализацией

- Какой сотрудник подразделения сверяет карточки и разрешает обновление конкретной версии каталога?
- Какие поля действительно требуются для схем текущих работ и какие из них можно показывать каждому участнику процесса?
- Где должен храниться каталог и как будут устроены доступ, резервное копирование и журнал изменений?
- Как часто и кем выполняется сверка ПУ-66 с фактическим состоянием переезда?
- В каком виде идентификатор старого JSON связывается с проверенной записью и как обрабатывается отсутствие совпадения?

До ответов на эти вопросы этот документ не является утверждённым регламентом. Импорт `v: 1` продолжает хранить старый ключ без проверки по ПУ-66; автоматическое построение или согласование схемы на основании такого ключа недопустимо.
