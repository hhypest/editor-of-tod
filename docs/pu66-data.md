# Данные ПУ-66: локальный реестр и порядок актуализации

Первая приёмка 29.10.2026 на a5ad72f: #110 принят (PU01–PU12). По #103 п. 8 уточнён как полная длина ответственности за текущий ремонт, симметрично от оси переезда. Максимальный фронт ограничен этой длиной и общим параметром (по принятому решению 45 м); отгон и буфер не входят. Подстановка выбирает сплошной фронт и вариант по порогу; свыше 30 м возможен отдельный переход на частичный Б.34. [Результат и повторная проверка доработки](acceptance-0.3.0-2026-10-29.md).

**Решение владельца от 25.10.2026 (#110):** в схемах используются карточки ПУ-66, импортированные техническим специалистом. Ежегодное переутверждение карточек, его организация и удостоверение актуальности относятся к использующей организации и специалисту, **вне ответственности репозитория и разработчика**. Эта процедура не является условием разработки или выпуска ПО. Существующий локальный журнал сверок остаётся средством учёта, не удостоверением карточки разработчиком.

Карточки конфиденциальны и остаются в локальной SQLite вместе с исходными XLSX. В публичных примерах используются только вымышленные сведения. Обновление реестра не переписывает исторические снимки проектов; новая редакция выбирается явно после сравнения.

## Утверждённые поля для схемы и листа

| Поле                         | Принятое решение                                                                                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ширина                       | Ширина **проезжей части**. Ширина полосы не выводится простым делением                                                                                      |
| Видимость                    | **Все значения, имеющиеся в карточке**, с сохранением объектов наблюдения, направлений и единиц; видимость поезда и встречного автомобиля не объединяется   |
| Автомобильная дорога         | Наименование автомобильной дороги                                                                                                                           |
| Железнодорожное наименование | Километр, пикет, станция/перегон                                                                                                                            |
| Интенсивность автомобилей    | **Авт/ч**, исходя из нормативных параметров, которые устанавливает и подтверждает технический специалист; произвольный коэффициент по умолчанию не вводится |

Ключ, редакция и происхождение остаются техническими метаданными снимка. Решение разрешает перечисленные данные для схемы/листа, но не публикацию полной карточки или её персональных сведений. Связь п. 8 с фронтом подтверждена в первой приёмке; повторная проверка её доработки остаётся отдельным результатом #103.

**Статус реализации:** в v11 `/scheme`, сравнение, снимок и лист содержат утверждённые поля, включая участок/станцию и видимость по объектам/направлениям/годам. #110 принят на a5ad72f 29.10.2026. `/norms` остаётся отдельной локальной выборкой для расчётов и просмотра технической таблицы; её лишние сведения в проект не экспортируются. Старые снимки не дополняются автоматически.

## Перед получением данных

1. Зафиксировать подразделение-владельца каталога, источник карточек, дату их состояния, территорию охвата, порядок получения изменений и уполномоченного на сверку специалиста.
2. Установить состав полей для локального хранения и передачи согласующим организациям по принятому порядку. Реальные карточки, встроенные 73 записи старого HTML и сканы в GitHub не добавляются.
3. Применять утверждённый выше состав полей для схемы и сохранять необходимые метаданные: устойчивый идентификатор переезда, проверенные характеристики, важные для выбора варианта и размещения элементов, ссылка на источник, версия записи и дата сверки. Персональные данные и реквизиты, не необходимые для составления схемы, исключить из каталога.

## Сейчас реализовано локально

- `private-data/registry.sqlite` создаётся на компьютере составителя, исключён из Git и доступен приложению только через процесс на `127.0.0.1`.
- Можно вручную внести ключ, место, автомобильную дорогу, владельца, реквизиты и дату карточки, дату сверки и примечание. Исправление создаёт новую редакцию записи; устаревшая правка отклоняется.
- Резервная копия SQLite создаётся по кнопке в `private-data/backups/`; перед обновлением схемы базы новой сборкой программа снимает такую копию сама (`registry-before-update-…`). База не шифруется приложением; доступ контролирует операционная система и правила хранения организации.
- JSON-проект из старого редактора не заносится в реестр автоматически; само наличие ключа не означает сверку карточки.
- Команда `npm run import:pu66 -- файлы.xlsx...` сначала показывает план, `--apply` сохраняет оригиналы XLSX, извлечённые поля и техническую таблицу в SQLite. Повторный неизменённый файл пропускается, изменённый создаёт редакцию. Перед записью создаётся резервная копия.
- В локальном интерфейсе можно выбрать до 100 XLSX по 4 МБ (не более 40 МБ в сумме), увидеть действие по каждой карточке и только после подтверждения записать пакет в SQLite. Сервер повторно проверяет файлы и отпечаток плана; если реестр изменился после просмотра, запись отклоняется и нужен новый просмотр. Перед изменением создаётся одна резервная копия на пакет. Файлы не передаются внешнему сервису; CLI остаётся для больших пакетов.
- Ключ участковой карточки — `участок:км:пк`. Станционная карточка получает ключ `ст.<станция>:км:пк:к<номер карточки>`, чтобы несколько переездов одной станции с одинаковой привязкой не перезаписывали друг друга. SQLite v9 разделяет ранее слитые редакции по номеру карточки и сохраняет прежние ключи как псевдонимы: если за старым ключом стояла одна карточка, проект продолжает открываться; если несколько, API возвращает 409 и проект нужно привязать к карточке заново.
- Четыре предоставленных образца XLSX успешно проходят локальный разбор текущим импортёром. Результаты разбора и сами книги не входят в публичные тесты; там используются только вымышленные карточки.
- Команда `npm run samples:pu66` создаёт пять полностью вымышленных XLSX с расположением полей наблюдаемых форм (четыре заголовка в строке 5, один в строке 4; станционная карточка без участка имеет заполненную станцию). Файлы записываются в исключённый из Git `local-input/examples-pu66/`, реальные сведения и оформление оригиналов не копируются. Интеграционный тест проверяет создание новой SQLite, импорт обеих версий расположения, последующий импорт PNG и повторное открытие базы. Учебные записи не отмечаются прошедшими ежегодную сверку.
- В «Реестры» → «Импорт Excel и знаков» можно отдельно записать фактическую дату и подразделение или ответственного за сверку выбранной редакции и просмотреть историю выбранной карточки. Записи ведутся в локальной SQLite без изменения XLSX или JSON-проекта. Для статуса берётся самая поздняя фактическая дата текущей редакции, даже если более ранняя сверка внесена в журнал позже. История показывается в порядке внесения. Следующий срок вычисляется как 30 января следующего года; 30 января показывается напоминание, позже — просрочка. Импорт новой редакции не переносит отметку со старой. Сам по себе импорт не означает сверки.
- Парсер принимает показанные примеры формы ПУ-66: один лист, заголовок «Карточка №», расположение строк относительно него, таблицу с 30 пунктами и два года фактических данных. Иные редакции формы отклоняются для ручного сопоставления, а не читаются по случайным координатам.
- Локальная сводка для составителя показывает часть данных для проверки. Список `/api/pu66` дополнительно содержит участок и станцию: они нужны только для поиска карточки в локальном интерфейсе и в проект не записываются. Отдельная выборка `/api/pu66/{ключ}/scheme` содержит внутренний ключ, местоположение, подпись оси, название дороги, ширину проезжей части, номер и время обновления редакции. Она не включает полный XLSX, техническую таблицу, персональные данные, движение или видимость. Разрешённый состав утверждён выше; расширение реализации выполняется отдельно в #110.
- При выборе составитель видит сравнение со сведениями уже открытого проекта; обновление записи во время выбора блокирует применение до повторного просмотра. JSON содержит отдельный небольшой снимок и номер редакции. Изменение локальной карточки не переписывает прежние проекты, обновление снимка выполняется только явным действием. Выбор из реестра не означает предметной проверки и не заполняет дату сверки.
- На черновом листе после явной привязки показаны место переезда, подпись оси, название автомобильной дороги и ширина проезжей части из закреплённой редакции. Остальные поля ПУ-66 и полный файл на лист не попадают. Состав полей и ограничения по двум предоставленным образцам описаны в [разборе листов Б.33/Б.34](reference-schemes.md).

## Исключение, возврат и преемник

В «Реестры» → «Карточки и нормативы» блок «Действующие и исключённые ПУ-66» управляет импортированными книгами. Ручные справочные записи ниже — отдельный справочник. Найдите карточки, отметьте до 100, укажите дату и составителя. Для исключения выберите причину; «Другая причина» требует пояснения. Необязательный преемник должен быть другой действующей карточкой, предварительно импортированной с новым ключом. Просмотрите список, затем подтвердите действие: сначала создаётся резервная копия, затем записывается журнал. Если запись или статус изменились, нужен новый просмотр.

Исключённые карточки скрыты из нового проекта, привязки, ежегодной сверки и счётчика начальной настройки. В списке «Исключённые» остаются причина, дата и история действий. Возврат выполняется тем же порядком с датой, составителем, просмотром и копией. Исходные XLSX, все редакции и журнал сверок не удаляются.

Старые проекты открываются с прежним снимком. Этап 1 сообщает об исключении и предлагает сравнить преемника; автоматической замены нет. На этапе 4 нужно проверить допустимость прежнего источника и поставить отдельную отметку. Повторное исключение делает прежнюю отметку устаревшей. Перед печатью и выгрузкой PNG статус проверяется повторно.

Повторный XLSX-импорт показывает исключение и может обновить редакцию без возврата. Для возврата отметьте конкретные карточки в плане, укажите дату и составителя, заново нажмите «Просмотреть изменения» и подтвердите импорт. Командный импорт не возвращает исключённые карточки. Полное удаление книг и истории не входит в этот блок.

Журнал и соответствие преемника остаются локальными; JSON-контракт проекта не расширяется. Уточнение обработки старых ключей — [ADR-0005](adr/0005-pu66-lifecycle.md).

Сводка и редакция преемника показываются в плане и входят в его отпечаток. Для выпускного листа используйте кнопку печати: Ctrl+P и меню браузера без свежей подготовки выводят причину остановки. Допуск действует только на один вызов печати; печать черновика из меню остаётся доступной.

## Дальнейший порядок актуализации

1. Получить разрешённую выгрузку от владельца данных и сохранить оригинал отдельно от приложения с установленным доступом. Для разработки и CI использовать только вымышленные примеры `TEST-001`, `TEST-002` и другие обезличенные фикстуры.
2. Для других редакций ПУ-66 описать формат и сопоставление полей. Явно указать единицы измерения, обязательность, допустимые значения, способ указания отсутствующих сведений и правила нормализации идентификаторов.
3. Проверить каждую запись на дубликаты, пропущенные поля, неоднозначные идентификаторы, неверные единицы и устаревшую дату сверки. Ошибки представить на просмотр ответственному, не исправлять их автоматически без следа.
4. Перед применением показать число новых, изменённых и исключённых записей. Специалист сверяет выборку с оригиналами и подтверждает версию каталога. Нынешний реестр хранит дату, редакцию и подразделение или ответственного; документальное основание и итог сверки по каждому пункту ещё следует определить.
5. При реализации #110 проверить соблюдение утверждённого выше состава полей и их единиц. Уже сохранённые схемы сохраняют свой снимок; редакции карточек остаются в локальной базе для воспроизведения.
6. Проверить импорт на обезличенных сценариях: корректный переезд, отсутствующий идентификатор, конфликт дубликатов, изменение владельца дороги и исправление характеристики. Затем проверить ограничения доступа и восстановление предыдущей версии каталога.

## Решения перед реализацией

- Какой сотрудник подразделения сверяет карточки и разрешает обновление конкретной версии каталога?
- Утверждённый состав полей приведён выше; ограничение доступа к полной карточке определяет использующая организация.
- Где должен храниться каталог и как будут устроены доступ, резервное копирование и журнал изменений?
- В каком виде идентификатор старого JSON связывается с проверенной записью и как обрабатывается отсутствие совпадения?

Этот документ фиксирует контракт ПО и решение владельца; организационный регламент ведения и ежегодного переутверждения карточек не устанавливается репозиторием. Импорт `v: 1` продолжает хранить старый ключ без проверки по ПУ-66; автоматическое построение или согласование схемы на основании такого ключа недопустимо.

Длина пересечения из технического пункта 8 и суточная интенсивность остаются в локальной карточке и её сводке, но не включены в выборку `/scheme` и JSON проекта. Для нормативных подсказок локальный редактор читает отдельную выборку `/api/pu66/{ключ}/norms`: категорию дороги, суточную интенсивность и число поездов, видимость и техническую таблицу (пункт, показатель, норма, фактические значения) без персональных данных. Она показывается только на этапе «Схема движения» и не записывается в проект и на лист. Суточная интенсивность пересчитывается в авт/ч только по доле часа пик, которую составитель подтвердил с основанием в «Нормативных параметрах»; результат попадает в проект, лишь когда составитель подставит его кнопкой и применит правки. Графа «Норма» сравнивается с фактом только для числовых норм («не менее», «не более», число; несовпадение с точным числом тоже считается расхождением); отклонение показывается как повод для проверки, а не как ошибка карточки. По категории дороги вне населённого пункта предлагается строка табл. 1 ГОСТ Р 52289 и кнопка выбора типоразмера (I–IV); число полос по категории составитель проверяет сам. Расширение белого списка для листа требует определения состава передаваемых сведений владельцем данных.

## Реализация утверждённого снимка v11 — 28.10.2026

Для #110 расширены API `/scheme`, сравнение перед закреплением, снимок и лист: добавлены участок/станция и разделы видимости с сохранением объектов, направлений и значений обоих годов. Графа «Норма», остальные технические строки, персонал, суточная интенсивность и полный XLSX в снимок не входят. Прежняя реализация выше описывает исторические ограничения; текущий контракт — [формат v11](scheme-format.md#снимок-пу-66-v11-110).

Старые снимки сохраняются без дополнения при открытии; новые сведения требуют явного сравнения/закрепления. Расчёт авт/ч использует подтверждённую долю часа пик; подстановка из другой редакции карточки заблокирована до закрепления. Автоматические сценарии используют вымышленные карточки. Приёмка точной Windows-сборки по #110 ещё требуется.
