# Подготовка и передача выпуска

Тип: действующий процесс для разработчика и владельца выпуска. Сверено 30.10.2026 по [windows-exe.yml](../../.github/workflows/windows-exe.yml), [CI](../../.github/workflows/ci.yml) и [проверке версии](../../scripts/__tests__/release-checksums.test.ts). Процесс не назначает номер следующей версии и не запускает публикацию. Результаты 0.2.0 находятся в [отдельном протоколе](reports/2026-10-24-release-0.2.0.md).

## До тега

1. Определите выпускаемую версию, состав и оставшиеся ограничения по [ROADMAP](../../ROADMAP.md) и [индексу приёмки](0.3.0/README.md). Зафиксируйте решение специалиста для точной сборки; открытый PR или успешный CI сами по себе не означают приёмки.
2. Согласуйте версию в package.json, обоих корневых полях package-lock.json и заголовке CHANGELOG `## [<версия>]`. Это проверяет release-checksums.test.ts. Не меняйте посторонние части lockfile ради номера версии.
3. На итоговом коммите выполните [общий check и Chromium/Firefox](../engineering/testing.md). Запишите SHA, ссылки на CI, ручные сценарии и ограничения. README/ROADMAP называют фактическое состояние кандидата.
4. Тег ставится на проверенный коммит, включённый в main. Новые результаты другого коммита не приписываются принятой сборке.

## Тег

Имя тега равно версии package.json, без префикса `v`. Команды ниже — **шаблон**, заполнители нужно заменить согласованной версией и полным SHA; это не указание выпускать 0.2.0 или текущую dev-версию:

```text
git tag -a <версия> -m "editor-of-tod <версия>" <полный-SHA>
git push origin <версия>
```

Тег не переставляется. Исправление после тега получает новую версию и собственный результат проверки. Сам push тега не запускает существующий CI: ci.yml настроен на main и PR, а Windows exe — только на workflow_dispatch. Сопоставьте уже выполненный CI с точным SHA тега и отдельно проверьте готовый exe.

## Ручная сборка exe

GitHub → Actions → «Windows exe» → «Run workflow». Для выпуска укажите согласованный тег в поле «Тег версии»; собирается refs/tags этого имени. Без тега собирается выбранная ветка для проверки. В Summary проверьте тип источника, версию и SHA.

Шаблон вызова из командной строки после подстановки согласованной версии:

```text
gh workflow run windows-exe.yml -f tag=<версия>
```

Workflow отклоняет несовпадение тега и package.json, собирает переносной файл, устанавливает Chromium/Firefox и проверяет готовый exe через TOD_E2E_EXE. Итог — артефакт `editor-of-tod-<версия>-<коммит>-win-x64` и суммы в Summary. Ошибка запуска workflow, браузера или теста не считается успешной сборкой. Артефакт ограничен сроком хранения; опубликованный выпуск оформляется отдельно человеком.

## Комплект и рабочее место

Скачайте артефакт именно этого запуска. Передаются все пять файлов вместе: editor-of-tod.exe, LICENSE.txt, LICENSE.ru.txt, THIRD_PARTY_LICENSES.txt и SHA256SUMS.txt. Запишите номер запуска и SHA тега в задачу выпуска. Сверяйте суммы с Summary того же запуска: сборка на другой машине может иметь другую сумму.

Проверка программы в PowerShell:

```powershell
Get-FileHash .\editor-of-tod.exe -Algorithm SHA256
```

Результат должен совпасть со строкой editor-of-tod.exe в SHA256SUMS.txt; сверьте также три файла лицензий. На Linux полный комплект проверяется `sha256sum -c SHA256SUMS.txt`. После проверки сумм выполните ручной запуск на рабочем месте: первый/повторный запуск, обновление с backup, сохранность проектов/recovery, печать и PNG по затронутому чек-листу. Windows Node CI не заменяет готовый exe, автоматический прогон не заменяет предметную приёмку.

Обновление составителя — по [руководству](../guide/projects-and-recovery.md): закрыть программу, сохранить данные и копии, заменить файлы программы, сохранить private-data. Перед миграцией поддерживаемой старой базы создаётся обязательная копия; отказ блокирует обновление. Рабочие карточки, PDF, база и backup в дистрибутив не включаются.

## После передачи

Зафиксируйте опубликованный тег/коммит, номер сборки, суммы, проверки и решение о передаче в датированном [протоколе](../catalog.md#протоколы-конкретных-проверок). Обновите текущий статус и начните новый Unreleased в CHANGELOG. Закрывайте задачу выпуска по факту готового комплекта и принятого результата. Для кандидата ведите отдельные замечания обкатки; исправление получает следующую согласованную версию.
