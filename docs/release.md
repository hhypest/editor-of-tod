# Выпуск версии

Порядок выпуска релиз-кандидата и версии: что делает разработчик, что — владелец репозитория и что получает составитель. Приложение не публикуется автоматически: тег ставит и сборку запускает человек.

## Выпуск 0.2.0

24.10.2026 владелец подтвердил успешную приёмку RC2 (35 из 35, без замечаний) и поручил выпуск `0.2.0`. Краткий результат — в `TESTING.MD`; исходный отчёт с рабочими примерами остаётся локальным. При подготовке согласованы Oxlint и его плагин после обновлений зависимостей. Форматы JSON v10 и SQLite v13 сохраняются.

Тег `0.2.0` без `v` ставится после слияния подготовки выпуска и успешного CI на коммит слияния; `windows-exe.yml` запускается с `tag=0.2.0`. Проверки `npm run check` и Playwright должны пройти для коммита тега, а браузерные сценарии — также на собранном exe. Пять файлов комплекта и SHA-256 размещаются в выпуске GitHub и фиксируются в #102. После передачи закрывается #102 и начинается следующая веха.

## Перед тегом

1. Задачи вехи закрыты или перенесены, приёмка на рабочем месте записана в `TESTING.MD` и в задаче приёмки.
2. Версия одинакова в `package.json`, `package-lock.json` (оба поля `version` корня) и в заголовке раздела `CHANGELOG.md` (`## [0.2.0-rc.1] — дата`). Это проверяет `scripts/__tests__/release-checksums.test.ts`. Поднимая версию, правьте lockfile той же версией npm, что в CI (Node.js 24), или только два поля корня: npm 10 переписывает другие поля lockfile.
3. На `main` проходят `npm run check` и `npm run test:e2e`. Каждый браузерный сценарий должен проходить и отдельно (`npx playwright test tests/e2e/<файл>.spec.ts:<строка>`): сценарий не должен зависеть от данных, оставленных предыдущим.
4. README, ROADMAP и `docs/` называют текущее состояние кандидата.

## Тег

Тег — точная версия из `package.json`, без префикса `v`: `0.2.0-rc.1`. Ставится на коммит слияния в `main`, по которому прошла приёмка:

```bash
git tag -a 0.2.0-rc.1 -m "editor-of-tod 0.2.0-rc.1" <коммит>
git push origin 0.2.0-rc.1
```

Тег не переставляется: исправление после тега — новая версия (`0.2.0-rc.2`).

## Сборка exe

GitHub → Actions → «Windows exe» → «Run workflow». Ветку в списке «Branch» оставьте `main`, в поле «Тег версии» впишите тег (`0.2.0-rc.1`) и нажмите «Run workflow»: собирается коммит тега. То же из командной строки: `gh workflow run windows-exe.yml -f tag=0.2.0-rc.1` (или `--ref 0.2.0-rc.1` — запуск с самого тега). Сборка:

- останавливается, если тега нет или он не совпадает с версией в `package.json`;
- собирает `editor-of-tod.exe`, проверяет его всеми браузерными сценариями;
- записывает `SHA256SUMS.txt` — SHA-256 программы и трёх файлов лицензий;
- показывает суммы на странице запуска (Summary) и сохраняет артефакт `editor-of-tod-<версия>-<коммит>-win-x64` на 90 дней.

Запуск без тега собирает выбранную ветку — для проверки; такой файл составителю как версия не передаётся. В заголовке Summary видно, что собрано: «тег …» или «ветка …».

## Передача составителю

1. Скачайте артефакт и распакуйте: `editor-of-tod.exe`, `LICENSE.txt`, `LICENSE.ru.txt`, `THIRD_PARTY_LICENSES.txt`, `SHA256SUMS.txt`. Передаются все пять файлов вместе.
2. Запишите суммы из `SHA256SUMS.txt` в задачу выпуска (для 0.2.0-rc.1 — #101) вместе с номером запуска Actions.
3. Составитель проверяет файл на рабочем месте в PowerShell:

   ```powershell
   Get-FileHash .\editor-of-tod.exe -Algorithm SHA256
   ```

   Значение (без учёта регистра букв) должно совпасть со строкой `editor-of-tod.exe` в `SHA256SUMS.txt` и в задаче выпуска. На Linux — `sha256sum -c SHA256SUMS.txt`.

4. Обновление на рабочем месте — по [руководству составителя](getting-started.md): сначала копия папки вместе с `private-data`, затем замена exe. Перед изменением базы программа сама сохраняет копию `registry-before-update-…`.

Суммы зависят от версии Node.js и системы сборки: у файла, собранного на другой машине, сумма другая. Сверяйте с суммами того запуска, из которого взят файл.

## После выпуска

- Задача выпуска закрывается, когда тег создан, exe и суммы переданы, а `npm run check` и Playwright прошли на теге (Actions по тегу проверяет exe).
- Раздел `[Unreleased]` в CHANGELOG начинается заново; новые записи — над разделом выпущенной версии.
- Для релиз-кандидата дальше — обкатка (РК5, #102): в `main` принимаются только исправления, каждое — с новым кандидатом `0.2.0-rc.N` или в итоговую `0.2.0`.
