# ADR-0012: модель примыканий и исторических связей в JSON v12

Дата: 01.11.2026. Статус: **реализован первый срез модели #107; геометрия, редактор и приёмка полной П6 предстоят**. Основание объёма — [согласованный контракт](../plans/notes-and-junctions.md) и решения Д2–Д5/Д9, J1–J4/РП1–РП7. Этот ADR не утверждает новые нормативные правила расстановки.

## Контекст

До v12 сведения `junc`/`tee` жили только в исходном JSON. #277 сохранил связанные объекты и запретил разрушительную перестройку; #278 добавил отображение табличек. Нужна модель, которую можно сохранять и проверять независимо от координат листа, с последующим подключением геометрии и автоматики.

## Решение

В проект добавляется обязательный `roadLayout`, формат повышается до v12. SQLite остаётся v13: существующие репозитории уже хранят версионированный JSON.

| Поле                   | Смысл и ограничения                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nodes`                | Прямоугольное боковое `junction` или конечный `terminal-tee`; не более одного конечного Т-перекрёстка. Косые/сквозные пересечения не моделируются.                                                            |
| `nextNodeId`           | Следующий устойчивый положительный ID в отдельном от объектов пространстве; выше всех занятых ID. Порядок списка не задаёт идентичность.                                                                      |
| `position`             | `approach: left, from: L0` либо `approach: right, from: E`; `metres` — расстояние до оси узла по Д2. Ноль допустим, отрицательные/бесконечные значения запрещены.                                             |
| `junction`             | Сторона `up/down`, вид `road/yard`, название и сохранённый запрос бокового предупреждения `sideWarningRequested`; сам запрос не запускает автоматику на выезде.                                               |
| `terminal-tee`         | Подписи верхней и нижней ветвей. Известные `n1/n2` перенесены как `up/down` по рисунку рабочего прототипа.                                                                                                    |
| `sheetOffsetXSvg`      | Независимый условный отступ рисунка от L0/E. `null` означает отсутствие сохранённого отступа; из него не выводятся метры.                                                                                     |
| `links`                | Существующие `placementId` и `nodeId`, назначение `main-repeat/side-warning/tee-branch`, происхождение `manual/legacy-v1`. Один объект связан не более чем с одним узлом; назначение соответствует виду узла. |
| `links[].installation` | Независимое расстояние установки стойки с явно выбранной точкой `L0/E/node-axis`; `null` означает неизвестное расстояние. Для элемента, не являющегося стойкой, расстояние не задаётся.                       |

Значение таблички остаётся в существующем коде знака (`8.1.3_120`), разбираемом общим обработчиком. Оно не дублируется новым изменяемым полем. Например, 120 м до узла, 50 м установки от L0 и «120 м» на табличке — независимые данные. Это проверка контракта, не новое правило размещения. Физическое размещение на ветви и применимость источников требуют следующего шага.

## Миграция и сохранность

Читатель v11 и его снимок ПУ-66 зафиксированы в `src/domain/formats/frozen/`, независимо от текущих подсхем. v1 и v2–v11 поднимаются до v12 в памяти. Чтение SQLite не переписывает историю; явное сохранение создаёт новую редакцию.

Для валидного исходника v1 сохраняются IDs `junc`, подход/сторона/вид/название, `d`, запрос предупреждения и `px`. Включённый `tee` получает ID после максимального ID примыкания; выключенный не создаёт узла. Повторное открытие v12 читает уже сохранённую модель и не строит её повторно из исходника. Исходный JSON остаётся точным.

Исторические `jrep/jside/tee` становятся связями только при единственной однозначной ссылке на существующий узел и сохранившийся объект того же вида. Удалённые объекты не воссоздаются; текущие положения, знаки, ручные правки и флаги объектов не заменяются. Неоднозначные/отсутствующие ссылки, `vert/sc` и неизвестные поля остаются в исходнике. Старый v11 с повреждёнными расширениями продолжает открываться под прежней защитой, без выдуманной модели.

`legacy-v1` означает только историческую связь: это не автоматическое владение и не проверка точного совпадения по РП7. Автоматические/изменённые/исключённые состояния, rule IDs и preview ещё не реализованы; их будущий persisted контракт требует отдельного версионированного изменения. Удаление связанной стойки удаляет её связь в той же операции; одна отмена восстанавливает обе. Узлы и их ID сохраняются.

## Интеграция и границы

Модель проходит импорт/экспорт, локальное сохранение, историю, восстановление и общий undo/redo. На этапе «Знаки и объекты» показывается сводка сохранённых узлов и числа распознанных связей. Редактирование узлов и рисунок ветвей ещё не включены.

Перестройка и выпуск закрыты для любых непустых узлов v12, включая созданные без старого исходника. Прежняя защита raw source также остаётся: удаление модели из файла не скрывает неподдержанную старую геометрию. Сохранение/JSON и доступный черновик остаются средствами сверки, а не готовым результатом П6.

## Альтернативы и последствия

- Оставить сведения только в исходнике: отсутствуют проверяемые ID/ссылки, дальнейшая геометрия снова зависит от разбора HTML-формата.
- Вписать поля в v11 без повышения версии: прежний строгий читатель не понимает новое содержимое, а формат становится неоднозначным.
- Восстановить объекты из raw source: это вернуло бы удалённые стойки и заменило текущие ручные изменения.
- Уже сейчас переносить всю автоматику прототипа: это смешало бы подтверждённые данные модели с ещё не проверенными правилами и РП1–РП7.

Выбран отдельный срез с явной версией и действующей защитой. Новые правила, массовое владение объектами, геометрия и снятие ограничений рассматриваются отдельно по [чек-листу П6](../verification/0.3.0/junctions-acceptance.md). А5/#256 не объявляется завершённым этим изменением: общая переработка codec остаётся самостоятельной.
