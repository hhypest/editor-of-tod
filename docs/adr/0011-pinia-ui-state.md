# ADR-0011: владельцы общего состояния Vue и постепенный переход на Pinia

Дата: 27.10.2026. Статус: **принято; А4 завершён, интеграция потребителей продолжается**. Подготовка принята в #227. Pinia 4.1.0 и владельцы общего состояния включены в main через #228–#232. Текущий завершающий шаг реализации — [основные представления читают stores](../refactoring/pinia-view-consumers.md) по [карте перехода](../refactoring/pinia-state-plan.md). Итоговые прогоны отложены до полного технического этапа. Уточняет клиентскую часть ADR-0006, не меняет серверный ADR-0010.

## Контекст

После #136 `App.vue` создаёт одну `useProjectSession`, передавая её дочерним представлениям. Внутри уже выделены документ, история, неприменённый ввод, cursor, recovery и прикладные операции. Сохранность обеспечивают существующие `RecoverySession`, `SaveProjectRevision` и `RestoreProjectRevision`, а не способ объявления Vue refs.

До переноса #191 кроме этой сессии общее состояние существовало в module-level refs `useNormativeRules` и `usePu66Status`. У параметров одна выполняющаяся загрузка; статус ПУ-66 разделяется по ключу и перечитывается, если реестр изменился во время запроса. Навигация принадлежит корневому компоненту; формы и выбранные файлы принадлежат своим компонентам. Единого store для всего этого пока нет.

Владелец выбрал Pinia первой задачей после А4. Требуется явное владение общими данными, поддержка TypeScript и диагностики, без новой сессии, очереди записи или изменения нормативного поведения. Ускорение приложения этим решением не обещается.

## Решение

Подключить один `createPinia()` к одному Vue app в `src/main.ts` после завершения А4. Stores создаются в контексте этого app; импорт модуля не создаёт store и не запускает HTTP или recovery. Новый тест получает собственный экземпляр Pinia. Разные окна продолжают иметь независимые владельцев recovery и курсоры, взаимодействуя через прежний локальный API.

Использовать setup stores для общего реактивного состояния. Предметные функции и application-сценарии не импортируют Pinia или Vue. Stores и совместимые composables относятся к UI-адаптерам; HTTP остаётся в `src/services`, SQLite — на сервере. Зависимости `src/stores` не должны образовывать циклы с composables, компонентами или навигацией. Полная матрица проверок остаётся отдельной #184; запрет core → Pinia/stores требуется уже при первом исполняемом переносе.

Переносить по одному владельцу: нормативные параметры → кэш статусов ПУ-66 → общие данные документа/истории/неприменённого ввода → состояние навигации и обновления представлений. Для каждого владельца сохранять совместимый ref-based фасад до перевода всех его потребителей. Не оставлять параллельные module-level refs, вторую копию документа или синхронизацию двух состояний через watch. При деструктуризации использовать `storeToRefs`, сохраняя прежние `.value` в фасаде и типы props.

`useProjectSession` остаётся единственной сборкой рабочих операций в корневом компоненте. Store предоставляет данные; существующие адаптеры выполняют commit/open/history и команды сохранения над этими refs. Чтение store в дочернем представлении не вызывает `useProjectSession`, `new RecoverySession`, регистрацию browser events или создание таймеров. Browser lifecycle остаётся у корня: один start/stop и одна регистрация/снятие подписок. Обратный вызов открытия проекта связывается с навигацией в корне, а не хранится в store.

Основные представления ProjectHub/RegistryHub/EditorWorkspace получают data refs напрямую из stores. Корень передаёт только стабильные узкие объекты команд (шесть для ProjectHub, десять для EditorWorkspace); типы выводятся как Pick прежнего ProjectSession. 44 ключа совместимого фасада сохраняются. Leaf-формы и переиспользуемые domain-компоненты продолжают принимать узкие props/события и не получают весь store или корневую сессию.

Промисы выполняющихся запросов, cursor/generation, recovery repository/очередь, таймеры и обработчики DOM остаются деталями соответствующих адаптеров. Реактивное состояние setup store возвращается явно; не использовать скрытые refs как вторую модель данных. Не сериализовать store целиком, не добавлять persisted-state plugins, автосохранение в localStorage, аналитику или выгрузку содержимого store в диагностику. Прежний JSON-экспорт и SQLite/recovery остаются отдельными явными контрактами. Отмена/повтор пользователя продолжает использовать предметную историю, а не историю инструментов разработки.

Локальный ввод форм остаётся локальным. Существующие `pendingDetails`/`pendingPlacement` и `recoverySeed` нужны для восстановления; при переносе меняется только владелец этих refs, не создаётся ещё одна копия формы. Выбранные файлы/PDF, предпросмотр импорта, подтверждающий диалог и локальные busy/error не становятся глобальными без отдельной причины.

Навигация получает data-only `editorNavigation` store, включая общий guard `projectTabChosen`; DOM, watchers и startup HTTP остаются в единственном корневом адаптере. Два счётчика обновления каталогов получают отдельный `catalogRefresh` store, поскольку используются реестрами, редакторами, setup и листом. Локальное состояние одного мастера setup, startup/request guards и deferred sessionStorage остаются в корне; [обоснование границы](../refactoring/editor-navigation-store.md).

## Альтернативы

- Сохранить одни composables: меньше изменений, но не выполняет явное решение владельца об общем состоянии Pinia и сохраняет неявные module-level владельцев.
- Завернуть весь `useProjectSession` в `defineStore`: слишком тесно связывает срок жизни сессии с первым потребителем и компонентными lifecycle hooks. Не подходит для безопасного перехода.
- Ввести общий store вместо application и SQLite: смешивает долговременное хранение с UI, создаёт другую модель транзакций и конфликтов. Не принимается.

## Последствия и проверка

Выбрана Pinia 4.1.0, обязательный peer @vue/devtools-api 8.2.1 и транзитивный nostics 1.3.0. Их MIT-лицензии и тексты проверены; lockfile фиксирует версии/integrity, штатная сборка формирует уведомления по вошедшим модулям. Обновление Vue и посторонних зависимостей не входит в перенос.

Первые переносы проверили общий store для двух потребителей и изоляцию двух экземпляров Pinia. Последующие изменения сохраняют один документ/историю/recovery, dirty/pending ввод, cursor guards, конфликт 409 и одну очередь. **Уточнение владельца 27.10.2026:** #191 продолжаем интегрировать; окончательные проверки и тестирование состояния, полный `npm run check`, E2E и Windows exe выполняются после полного погашения технического долга. Это заменяет прежнее требование финальных прогонов на каждом шаге. Подготовленные, но не запущенные сценарии не считаются пройденными. Состав критериев указан в [плане](../refactoring/pinia-state-plan.md).

Vue Router, JSON v10/SQLite v13, нормативы, утверждённые поля #110, компоновка интерфейса и рисунок листа не меняются. Переход не начинает И4 или функции 0.3.0.

## Условия пересмотра

Пересмотреть границу владельца, если для неё нужны двусторонняя синхронизация состояния, второй recovery или зависимость domain/application от UI. Новые требования к нескольким одновременно открытым документам потребуют отдельного ADR. SSR, совместная работа и серверные аккаунты этим решением не вводятся.
