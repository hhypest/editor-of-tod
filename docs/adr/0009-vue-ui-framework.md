# ADR-0009: Vue для интерфейса; отказ от перехода на React и Angular

Дата: 24.10.2026. Статус: **принято; документирует и уточняет обоснование существующего выбора Vue из ADR-0001**. Основание — поручение владельца закрепить аргументы выбора и сознательный отказ от альтернатив. Не изменяет ADR-0006 и не объявляет И3 принятым.

## Контекст и критерии

Локальный редактор обслуживает одного составителя. Основные задачи интерфейса — формы условий и реквизитов, табличные параметры, SVG-лист, каталог знаков, предпросмотр импорта, история и восстановление ввода. Нужны понятный рабочий сценарий, сохранность незавершённых правок, согласованная сессия, контролируемые побочные эффекты и воспроизводимая проверка A4/PNG.

В коде уже используются Vue 3, TypeScript, Single-File Components, Composition API, Vite и `vue-tsc`. Клиент обращается к локальному Node.js API; production-интерфейс поставляется с exe как статические ресурсы. Требований к SSR, SEO, React Server Components или независимой серверной отрисовке сейчас нет. Предметная модель и выделенные сценарии не зависят от Vue.

Оцениваем соответствие текущим задачам, ясность владения состоянием, возможность отделять модель от представления, стоимость сопровождения и риск миграции. Сравнительных измерений скорости, памяти, размера дистрибутива и стоимости разработки на трёх реализациях не проводилось; такие преимущества не приписываем ни одному варианту. Владение командой каждым из трёх стеков отдельно не измерено.

## Решение

**Сохраняем Vue 3 + TypeScript для интерфейса. На React и Angular текущий продукт не переводим.** Новые сценарии и переработку интерфейса реализуем в этом стеке, сохраняя направление зависимостей из ADR-0006. Перенос интерфейса требует отдельного ADR с проверяемой пользой и планом сохранности данных.

## Аргументы за Vue

1. **Формы и лист описываются рядом с их поведением.** SFC соединяет шаблон, TypeScript и scoped-стили владельца; проект также выносит стили в отдельные файлы через `src`. Для данного редактора шаблоны HTML/SVG дают прямое описание полей, таблиц и листа. Это оценка удобства для существующего кода; React и Angular тоже способны реализовать этот интерфейс. Возможности SFC описаны в [официальном руководстве Vue](https://vuejs.org/guide/scaling-up/sfc).
2. **Реактивная оболочка отделяется от правил.** Composition API и composables позволяют вынести состояние формы и жизненный цикл. В проекте `useProjectSession`, `useProjectRevisionActions` и `useEditorNavigation` адаптируют независимую модель и сценарии; Vue не нужен для расчёта или проверки схемы. Composables сами по себе не обеспечивают Clean Architecture — направление зависимостей закреплено тестами и правилами импортов. См. [Vue: Composables](https://vuejs.org/guide/reusability/composables.html).
3. **Проверка TypeScript охватывает шаблоны.** В проекте строгая проверка выполняется отдельным `vue-tsc --build`. Одна сборка Vite не считается проверкой типов; это соответствует [официальному руководству Vue по TypeScript](https://vuejs.org/guide/typescript/overview).
4. **Можно менять рабочий сценарий постепенно.** Оболочка, формы и лист уже разделены на компоненты; сохранность ввода зависит от их времени жизни, единственной сессии и независимых операций. Переработка мастера и редактора возможна без одновременного переноса расчётов, SQLite и формата проектов.
5. **Сохраняется проверенная основа продукта.** Есть тесты импорта старых схем, конфликтов, восстановления, ручных правок, SVG/PNG и печати. При замене Vue пришлось бы заново реализовать и проверить UI-адаптеры, реактивность и жизненный цикл; достаточной пользовательской выгоды для этого сейчас не выявлено. Существующий код — аргумент стоимости перехода, а не доказательство технического превосходства Vue.

### Почему отказ от React осознанный

React — допустимый технический вариант. [Официальная документация допускает создание приложения с нуля, в том числе с Vite](https://react.dev/learn/build-a-react-app-from-scratch); [custom hooks](https://react.dev/learn/reusing-logic-with-custom-hooks) позволяют выделять повторно используемую логику. Поэтому аргументы «React требует SSR/Next.js», «нельзя отделить предметную модель» или «React не подходит для SVG» основанием решения не являются.

Для этого продукта переход потребует заменить шаблоны и Vue-адаптеры, заново подтвердить сохранность сессии, незавершённого ввода, очередей и листа. Эти работы конкурируют с исправлением уже выявленных затруднений составителя. Смена библиотеки сама по себе не устраняет лишние поля, переходы в общие формы и непонятную навигацию. Без отдельной доказанной потребности затраты перехода не оправданы.

### Почему отказ от Angular осознанный

Angular также подходит технически. [Официальный обзор](https://angular.dev/overview) описывает компоненты, signals, DI, router и средства форм. Единые платформенные соглашения могут быть полезны продукту с другими требованиями к командам и интеграции. Это достоинства альтернативы, а не основание считать её непригодной.

Здесь уже есть локальный API, собственные узкие интерфейсы сценариев и Vue-представления. Принятие соглашений Angular и перенос компонентов требуют отдельной работы; оснований, компенсирующих эту работу для текущего локального редактора, не установлено. Отказ не опирается на утверждения об обязательных NgModules, обязательном Zone.js или обязательном применении RxJS в каждом компоненте; не заявляет проигрыша Angular по скорости или безопасности.

## Последствия и обязательные ограничения

- Vue остаётся адаптером представления. Предметные вычисления, миграции, нормативные правила и выделенные прикладные сценарии не переносятся в компоненты ради удобства реактивности.
- Props/events и время жизни компонентов должны сохранять единый проект, историю и незавершённый ввод. Composable с побочными эффектами не подменяет прикладной сценарий; добавление `watch` требует ясных причин и обработки запоздалых ответов.
- Наличие `v-model` не считается подтверждением нормативного параметра или командой сохранения. Запись, отмена, предпросмотр и фактическая готовность выражаются явно.
- Vue не гарантирует удобство автоматически. Отрицательная приёмка И3 выявила проблему рабочего сценария; исправлять её следует устройством экранов и действий, с повторной проверкой составителем.
- Зависимость от формата SFC и Vue runtime остаётся сознательной ценой выбора на уровне UI. Изолированное ядро уменьшает объём возможной миграции, но не делает замену интерфейса бесплатной.
- Сохраняются проверка типов, границ, unit/API/browser-тесты и предметная приёмка. Новые router/store/DI/форменные библиотеки вводятся по конкретному требованию с отдельной оценкой, а не ради полноты стека.

## Условия пересмотра

Решение пересматривается при обязательной интеграции с корпоративной платформой, недоступной в текущем стеке; появлении специализированного компонента с доказанным преимуществом; измеренных и воспроизводимых проблемах Vue, не решаемых локальным изменением; существенном изменении состава сопровождения или жизненного цикла продукта. Размер команды или появление совместной работы сами по себе не предписывают React либо Angular.

Новый ADR должен показать конкретный сценарий, сравнение прототипов или измерений, объём замены UI-адаптеров, стоимость сопровождения и план проверки старых проектов, неприменённого ввода, восстановления, конфликтов и A4/PNG. До этого архитектурное направление и выбор Vue действуют.
