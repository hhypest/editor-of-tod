# Редактор СОДД для железнодорожных переездов

Веб-приложение для подготовки схем организации дорожного движения на период текущих работ на железнодорожных переездах. Проект развивается из автономного HTML-прототипа в платформу на Vue 3 и TypeScript. По сообщённому составителем порядку схему утверждает владелец автомобильной дороги (администрация или дорожная организация), согласовывает Госавтоинспекция. Реквизиты конкретных участников заполняются для каждой схемы. [Состав полей по предоставленным образцам Б.33/Б.34](docs/reference-schemes.md) описан без публикации рабочих листов.

**Состояние проекта:** можно создать проект без старого JSON, открыть файлы v1–v4, редактировать параметры и объекты, сохранять черновики с историей в локальной SQLite и скачивать копию `schemaVersion: 4`. Из импортированной карточки ПУ-66 можно явно закрепить ограниченный набор полей и номер редакции после сравнения; обновление реестра не меняет прежний снимок проекта. В рабочей области доступны ручные стойки, надписи, регулировщики, машина прикрытия и элементы ограждения, перемещение и отмена действий. Панель проверки заполнения пересчитывает пропуски после применения правок и отдельно показывает пункты для ручной сверки. Условный печатный лист A4 приближен по композиции к образцам Б.33/Б.34 и показывает введённую размерную цепочку; координаты не являются масштабом местности. Есть локальные реестры ПУ-66, нормативных пунктов и знаков, импорт XLSX и обновляемого ZIP через браузер или CLI. Печать требует изображений из локального архива с указанной редакцией источника. Автосохранение, полноценный нормативный лист СОДД, автоматическая расстановка, отдельный экспорт PDF/PNG и согласование ещё не реализованы. Конфиденциальные данные в репозиторий не включены.

Интерфейс построен по четырём этапам: **исходные данные → схема движения → знаки и объекты → проверка и лист A4**. После открытия проекта лист в уменьшенном виде остаётся справа, а формы показываются только для текущего этапа. «Проекты» и «Реестры» открываются отдельными разделами. Изменения формы нужно применить перед сохранением и печатью; переход между этапами сохраняет неприменённый ввод в текущей вкладке.

## Что есть в исходном прототипе

Локальный файл `Схемы_ОДД_переезды.html` содержит варианты Б.33 и Б.34 ОДМ 218.6.019-2016, 73 записи о переездах, 420 изображений знаков, редактирование объектов на SVG-листе, сохранение и открытие JSON-проекта, автосохранение, отмену действий, печать A4/PDF и экспорт PNG. Руководство пользователя описывает эти возможности. Перечисление относится к **прототипу**, а не к приложению из этого репозитория.

При переносе функций требуется сохранить возможность открыть ранее сохранённый проект без потери важных правок, проверить нормативные правила и определить происхождение каждого набора данных и изображения. См. [план миграции](docs/migration.md) и [нормативную основу](docs/standards.md).

## Локальный запуск

Поддерживаются Node.js 24.12+ в пределах версии 24 (она указана в `.nvmrc`) и Node.js 26.7+ в пределах версии 26. Локальный API запускается Node.js напрямую из TypeScript-файлов.

```bash
npm ci
npm run dev
```

Откройте адрес Vite из терминала (`http://127.0.0.1:5173/`). Команда запускает интерфейс и локальный API на `127.0.0.1:4100`; оба доступны только с этого компьютера. Для работы с собранной версией: `npm run build`, затем `npm run local` и адрес `http://127.0.0.1:4100/`. Docker и внешняя база не нужны.

SQLite создаётся в `private-data/registry.sqlite`; каталог исключён из Git. Кнопка резервного копирования сохраняет согласованную копию в `private-data/backups/`. Файл **не зашифрован**: ограничьте доступ средствами операционной системы и храните резервные копии по правилам работы с конфиденциальными данными. Не добавляйте файл, черновики или выдержки ПУ-66 в коммиты, PR, публичные сообщения и вложения. В базе хранятся карточки, краткие записи об источниках, знаки и сохранённые черновики со всеми редакциями. Полный текст исходного JSON содержится в каждой редакции черновика. Открытие JSON-проекта в браузере не записывает его в SQLite автоматически; выбор XLSX для ПУ-66 также не меняет базу до подтверждения импорта.

При первом запуске локальный API сам создаёт SQLite без карточек ПУ-66 и знаков; четыре кратких указателя на ОДМ/ГОСТ уже есть в нормативном реестре. На странице «Проекты» появляется подсказка для импорта недостающих каталогов. Для проверки без рабочих данных создайте четыре полностью вымышленные книги в исключённой из Git папке:

```bash
npm run samples:pu66
```

Книги появятся в `local-input/examples-pu66/`. Они воспроизводят расположение полей предоставленных форм (в том числе смещение заголовка одной из них), но не содержат сведений из подлинных ПУ-66. В «Реестры» → «Импорт Excel и знаков» сначала загрузите свой ZIP с парами PNG и укажите редакцию источника, затем выберите четыре учебных XLSX либо разрешённые рабочие книги. Для каждой операции сначала просмотрите изменения и отдельно подтвердите запись. Учебные записи не отмечаются выверенными и не служат нормативными данными; подробная проверка описана в [TESTING.MD](TESTING.MD).

Для импорта ПУ-66 через интерфейс откройте «Реестры» → «Импорт Excel и знаков», выберите до четырёх разрешённых XLSX размером не более 4 МБ каждый, просмотрите карточки и отдельно подтвердите запись. Сервер повторно проверит книги и состояние реестра, затем создаст резервную копию перед изменением базы. Если карточка изменилась между просмотром и записью, повторите просмотр. Файлы отправляются только локальному API на этом компьютере; импорт не означает ежегодной сверки.

Для обновления знаков через интерфейс в том же разделе выберите архив ZIP, укажите документ и редакцию ГОСТ и сначала просмотрите изменения. PDF можно приложить для записи хеша источника; приложение не извлекает изображения из PDF и не подтверждает соответствие архива документу. После подтверждения новая редакция становится текущей, прежние PNG сохраняются в истории локальной SQLite, а отсутствующие в новом архиве коды больше не доступны на листе. Печать требует указанной редакции и всех использованных PNG. Схема v4 хранит коды без закреплённой версии изображений: после импорта другой редакции проверьте прежние проекты перед повторной печатью.

Для пакетного импорта через CLI остановите приложение и выполните предварительный просмотр и импорт:

```bash
npm run import:pu66 -- "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:pu66 -- --apply "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:signs -- "local-input/signs.zip"
npm run import:signs -- --apply "local-input/signs.zip"
```

Запуск команды без `--apply` только сообщает количество новых и изменённых записей. `--apply` сохраняет их с резервной копией; повторная загрузка того же файла не создаёт новую редакцию. CLI знаков помечает редакцию ГОСТ как неизвестную; для печати импортируйте архив через интерфейс с указанием редакции. Оригинал каждой ПУ-66 и полная извлечённая таблица остаются только в SQLite. Локальный интерфейс показывает краткую сводку; отдельный API для будущего листа выдаёт лишь место, осевую подпись, название дороги и ширину проезжей части. После фактической сверки линейным подразделением откройте «Реестры» → «Импорт Excel и знаков» и запишите дату и ответственного для конкретной редакции. Сверка проводится 30 января каждого года; импорт Excel сам по себе не фиксирует её проведение, новая редакция требует отдельной записи. Запись о сверке остаётся в локальной базе и не включается в экспорт проекта. Знаки хранятся как две версии PNG (с номером и без). Ранее созданные автоматической трассировкой SVG удаляются при обновлении локальной базы. См. [инструкцию проверки](TESTING.MD) и [каталог знаков](docs/sign-catalog.md).

В «Проекты» → «Новый проект» введите локальный идентификатор переезда, длины фронта, отвода, буфера и три скорости. Размеры незадействованного варианта остаются пустыми. На этапе «Исходные данные» выберите карточку ПУ-66, сравните поля с проектом и явно закрепите редакцию; это не подтверждает актуальность карточки. На этапе «Схема движения» уточняются размеры и параметры, на этапе «Знаки и объекты» работают поле и палитра. На этапе «Проверка и лист» видны пустые поля, отличия размерной цепочки от рисунка ОДМ и пункты ручной сверки, затем доступен полноразмерный черновой лист и кнопка «Печать черновика A4». Уменьшенный лист справа обновляется после применения правок. Отсутствие замечаний не означает соответствия нормам. Печатайте только для внутренней сверки: фактическая геометрия, нормативная расстановка и применимость ещё не подтверждены. Лист не берёт исходный JSON или полную карточку ПУ-66, но содержит отобранные конфиденциальные сведения; защищайте распечатки и файлы PDF. Старые v1/v2/v3 и редакции SQLite открываются с преобразованием в v4 без переписывания исходных снимков. Примените правки, сохраните локально или скачайте JSON v4 через «Действия с проектом»; обновление реестра ПУ-66 не меняет сохранённый проект автоматически.

Команды разработки:

| Команда                 | Назначение                                            |
| ----------------------- | ----------------------------------------------------- |
| `npm run dev`           | Vite и локальный API с SQLite на `127.0.0.1`          |
| `npm run local`         | Собранное приложение и API на `127.0.0.1:4100`        |
| `npm run import:pu66`   | Просмотр или импорт карточек XLSX в локальную SQLite  |
| `npm run import:signs`  | Просмотр или импорт пар PNG из ZIP                    |
| `npm run samples:pu66`  | Создать четыре вымышленные XLSX для локального теста  |
| `npm run check`         | Форматирование, линтеры, типы, тесты и сборка         |
| `npm run check:runtime` | Запуск API на временной SQLite напрямую через Node.js |
| `npm run test`          | Проверки модели и импорта проектов                    |
| `npm run format`        | Форматирование исходников и документации              |
| `npm run lint:fix`      | Автоматическое исправление части замечаний линтеров   |
| `npm run build`         | Проверка типов и сборка в `dist/`                     |
| `npm run preview`       | Локальный просмотр собранной версии                   |

Версии зависимостей зафиксированы в `package-lock.json`; CI выполняет `npm ci` и `npm run check` на Linux с Node 24 и на Windows с Node 26. Проверка прямого запуска API использует только временную SQLite в памяти и не открывает рабочую базу. Автоматическая публикация отсутствует: даже после сборки схема не считается проверенной или согласованной.

## Структура и процесс

- `src/domain/` — схемы данных, создание проекта, проверка JSON, чтение v1/v2/v3 и запись `schemaVersion: 4`, ограниченная привязка ПУ-66, команды изменения и история действий.
- `src/App.vue` — пошаговая навигация проекта, локальные разделы реестров и сохранения, постоянный предпросмотр листа.
- `src/components/` — формы параметров и свойств объектов, координатная рабочая область, черновой лист A4, палитра PNG, локальные реестры, каталог знаков, предварительный выбор варианта.
- `server/` — локальный API, импорт XLSX/ZIP и SQLite; конфиденциальные данные остаются в `private-data/`.
- `docs/scheme-format.md` — контракт нового файла и ограничения текущего импорта.
- `docs/migration.md` — инвентаризация автономного редактора и требования к совместимости.
- `docs/architecture.md` — границы модулей и модель будущей платформы.
- `docs/standards.md` — реестр нормативных источников и правила их проверки.
- `docs/pu66-data.md` — проект процедуры подготовки данных ПУ-66 для будущего каталога.
- `docs/reference-schemes.md` — состав полей листов Б.33/Б.34 по предоставленным образцам и вопросы предметной сверки.
- `docs/sign-catalog.md` — формат локального каталога изображений знаков.
- [`ROADMAP.md`](ROADMAP.md) — очередность работ и критерии готовности.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — правила кода, проверок и изменений.
- [`TESTING.MD`](TESTING.MD) — локальный запуск и проверка импорта на обезличенном примере.
- [учебные листы Б.33/Б.34](tests/fixtures/review-b33-v4.json) — два вымышленных JSON v4 для визуальной проверки компоновки; [Б.34](tests/fixtures/review-b34-v4.json) содержит ручных регулировщиков.
- [шаблон PR](.github/PULL_REQUEST_TEMPLATE.md) — что приложить к ревью.
- [`CHANGELOG.md`](CHANGELOG.md) — история изменений репозитория.

Изменения вносятся через ветку и pull request. Для шаблонов, знаков, расстояний и экспортируемого листа к PR прикладываются проверяемые примеры и ссылка на конкретную редакцию источника. Предметную корректность схемы оценивает ответственный специалист перед передачей на согласование.

## Данные и права

Исходный HTML содержит встроенные записи из карточек ПУ-66, изображения знаков и реквизиты организации. Исходные PDF стандартов и руководство пользователя также предоставлены для анализа. Эти материалы **не входят** в открытый репозиторий и **не подпадают** под его лицензию MIT. Перед публикацией любого набора переездов, изображения, полного текста стандарта или исходного прототипа отдельно проверяются права и допустимость раскрытия. Для локальных материалов предусмотрены игнорируемые каталоги `local-input/` и `private-data/`.

Импорт проверяет структуру файла, сохраняет исходный v1 JSON внутри новой копии, показывает перенесённые поля и предупреждения. Новый проект не забирает карточку ПУ-66 автоматически. При явной привязке JSON-копия и черновик содержат выбранные сведения из карточки; обращайтесь с ними как с конфиденциальными данными и не помещайте в GitHub. До сохранения проект находится в памяти браузера; при сохранении копия отправляется локальному API на `127.0.0.1` и записывается в SQLite. База не синхронизируется с GitHub. Приложение пока не проверяет соответствие схемы нормативам и не заменяет установленный порядок согласования.
