# Редактор СОДД для железнодорожных переездов

Веб-приложение для подготовки схем организации дорожного движения на период текущих работ на железнодорожных переездах. Проект развивается из автономного HTML-прототипа в платформу на Vue 3 и TypeScript. По сообщённому составителем порядку схему утверждает владелец автомобильной дороги (администрация или дорожная организация), согласовывает Госавтоинспекция. Реквизиты конкретных участников заполняются для каждой схемы. [Состав полей по предоставленным образцам Б.33/Б.34](docs/reference-schemes.md) описан без публикации рабочих листов.

**Состояние проекта (30 сентября 2026 года):** приложение закрывает основной сценарий составителя, но схема ещё не прошла предметную приёмку.

- Новый проект создаётся только по карточке ПУ-66 из локального реестра: без карточек в реестре начать схему нельзя. JSON v1–v6 открываются, редактирование и сохранение идут в формате `schemaVersion: 6`. Редакции хранятся в локальной SQLite, есть копии восстановления несохранённого ввода.
- На этапе «Знаки и объекты» собирается условный шаблон Б.33/Б.34 по рисункам ОДМ, ручные объекты при повторной сборке сохраняются.
- Лист A4 рисуется в SVG по оформлению локального редактора. После отметки составителя «Я проверил лист…» он печатается как выпускной (без пометки «черновик») и скачивается в PNG около 300 dpi.
- Каталог знаков извлекается из PDF ГОСТ Р 52290 (прежний способ — ZIP с PNG). PDF стандартов и методик хранятся в локальной библиотеке по редакциям.
- Числа правил (пороги интенсивности, отгон, таблица регулировщика, шаг скорости, типоразмеры) подтверждаются составителем по цитате из PDF действующей редакции. Сведения ПУ-66 (интенсивность, категория дороги, видимость, графа «Норма») подсказывают исходные данные схемы.
- Есть переносной `editor-of-tod.exe` для Windows без установки Node.js.

Чего ещё нет: примыканий и Т-образного перекрёстка, автоматической перестройки объектов при смене параметров, проверки листа на эталонах и маршрута согласования (см. [дорожную карту](ROADMAP.md)). Расстановка остаётся условной и проверяется составителем; отсутствие замечаний не означает соответствия нормам. Конфиденциальные файлы в репозиторий не включены.

Подробная справка для составителя встроена в приложение: кнопка «Справка» в верхней панели открывает раздел по текущему экрану, есть оглавление и поиск.

Интерфейс построен по четырём этапам: **исходные данные → схема движения → знаки и объекты → проверка и лист A4**. После открытия проекта лист в уменьшенном виде остаётся справа, а формы показываются только для текущего этапа. «Проекты» и «Реестры» открываются отдельными разделами. Изменения формы нужно применить перед сохранением и печатью; переход между этапами сохраняет неприменённый ввод в текущей вкладке.

При изменении проекта приложение через короткую задержку записывает в локальную SQLite отдельную копию восстановления, включая неприменённый ввод параметров и свойств объекта. Состояние записи видно в верхней панели. После повторного запуска откройте «Проекты» → «Копии восстановления» и выберите нужную копию; её можно удалить вручную. Копия не создаёт редакцию проекта, не заменяет явное «Сохранить локально» и не является JSON-экспортом. Если окно закрыто до появления надписи «копия восстановления записана» или локальный API недоступен, последние изменения могут отсутствовать в копии. При сохранении редакции эта копия удаляется. Копии содержат данные схемы и попадают в резервную копию SQLite; храните файл в защищённом локальном каталоге.

## Что есть в исходном прототипе

Локальный файл `Схемы_ОДД_переезды.html` содержит варианты Б.33 и Б.34 ОДМ 218.6.019-2016, 73 записи о переездах, 420 изображений знаков, редактирование объектов на SVG-листе, сохранение и открытие JSON-проекта, автосохранение, отмену действий, печать A4/PDF и экспорт PNG. Руководство пользователя описывает эти возможности. Перечисление относится к **прототипу**, а не к приложению из этого репозитория.

При переносе функций требуется сохранить возможность открыть ранее сохранённый проект без потери важных правок, проверить нормативные правила и определить происхождение каждого набора данных и изображения. См. [план миграции](docs/migration.md) и [нормативную основу](docs/standards.md).

## Локальный запуск

Поддерживаются Node.js 24.12+ в пределах версии 24 (она указана в `.nvmrc`) и Node.js 26.7+ в пределах версии 26. Локальный API запускается Node.js напрямую из TypeScript-файлов.

```bash
npm ci
npm run dev
```

Откройте адрес Vite из терминала (`http://127.0.0.1:5173/`). Команда запускает интерфейс и локальный API на `127.0.0.1:4100`; оба доступны только с этого компьютера. Для работы с собранной версией: `npm run build`, затем `npm run local` и адрес `http://127.0.0.1:4100/`. Docker и внешняя база не нужны.

SQLite создаётся в `private-data/registry.sqlite`; каталог исключён из Git. Кнопка резервного копирования сохраняет согласованную копию в `private-data/backups/`. Файл **не зашифрован**: ограничьте доступ средствами операционной системы и храните резервные копии по правилам работы с конфиденциальными данными. Не добавляйте файл, черновики или выдержки ПУ-66 в коммиты, PR, публичные сообщения и вложения. В базе хранятся карточки, краткие записи об источниках, знаки, сохранённые черновики со всеми редакциями и отдельные копии восстановления. Начиная с SQLite версии 7, исходный JSON новых редакций черновиков хранится один раз по SHA-256; прежние снимки не переписываются. SQLite версии 8 добавляет копии восстановления. Экспорт JSON остаётся самодостаточным. Открытие JSON-проекта в браузере не записывает его в SQLite автоматически; выбор XLSX для ПУ-66 также не меняет базу до подтверждения импорта.

Резервные копии автоматически не удаляются. Для просмотра политики хранения последних 20 копий не старше 90 дней (при этом всегда остаётся хотя бы одна) выполните `npm run backups:prune`. Проверьте список, затем при необходимости выполните `npm run backups:prune -- --apply`. Порог можно изменить: `--keep 30 --max-age-days 180`. Команда затрагивает только копии с именами, созданными приложением, в `private-data/backups/`; иные файлы остаются. До удаления убедитесь, что нужные копии перенесены в архив по правилам вашей организации.

При первом запуске локальный API сам создаёт SQLite без карточек ПУ-66, знаков и нормативных документов; четыре кратких указателя на ОДМ/ГОСТ уже есть в разделе «Карточки и нормативы». На странице «Проекты» появляется подсказка для импорта недостающих каталогов. Для проверки без рабочих данных создайте пять полностью вымышленных книг в исключённой из Git папке:

```bash
npm run samples:pu66
```

Книги появятся в `local-input/examples-pu66/`. Они воспроизводят расположение полей предоставленных форм (в том числе смещение заголовка одной из них), но не содержат сведений из подлинных ПУ-66. В «Реестры» → «Импорт Excel и знаков» сначала прикрепите PDF ГОСТ Р 52290 в «Нормативных документах» и извлеките из него знаки (или загрузите свой ZIP с парами PNG), затем выберите все пять учебных XLSX одной операцией; рабочие XLSX импортируйте только при разрешённом доступе. Для каждой операции сначала просмотрите изменения и отдельно подтвердите запись. Учебные записи не отмечаются выверенными и не служат нормативными данными; подробная проверка описана в [TESTING.MD](TESTING.MD).

Для импорта ПУ-66 через интерфейс откройте «Реестры» → «Импорт Excel и знаков», выберите до 100 разрешённых XLSX (не более 4 МБ каждый и 40 МБ в сумме), просмотрите карточки и отдельно подтвердите запись. Сервер повторно проверит книги и состояние реестра, затем создаст одну резервную копию на весь пакет перед изменением базы. Если карточка изменилась между просмотром и записью, повторите просмотр. Файлы отправляются только локальному API на этом компьютере; импорт не означает ежегодной сверки.

Числа правил (пороги интенсивности, отгон, таблица расстояний до регулировщика, шаг скорости, типоразмеры) подтверждаются в «Реестры» → «Нормативные параметры»: программа находит пункт в PDF действующей редакции, показывает цитату и предлагает значение, составитель подтверждает. После смены редакции подтверждение требуется заново ([docs/standards.md](docs/standards.md)). Для проекта с карточкой ПУ-66 на этапе «Схема движения» показаны интенсивность с пересчётом в авт/ч по подтверждённой доле часа пик, категория дороги с подсказкой типоразмера, видимость и графа «Норма» технической таблицы с отметкой расхождений.

Нормативные документы прикрепляются в «Реестры» → «Нормативные документы»: PDF (до 40 МБ) с обозначением, редакцией, датой введения и отметкой, если это изменение к стандарту. Обозначение и год подсказываются по имени файла (`GOST-R-52290-2024.pdf`). Перед записью показывается, какая редакция станет действующей и какую заменит, создаётся резервная копия. Действующей считается последняя редакция с наступившей датой введения; прежние остаются в библиотеке с отметкой «заменён» и открываются кнопкой «Открыть PDF». Раз в год приложение просит подтвердить, что действующая редакция не устарела: само оно внешние источники не проверяет. Если в библиотеке действует более новая редакция стандарта знаков, чем та, по которой загружен каталог или закреплены знаки проекта, об этом предупреждают раздел документов, импорт знаков и лист.

Для обновления знаков через интерфейс в том же разделе выберите PDF ГОСТ Р 52290 из библиотеки и нажмите «Извлечь знаки из PDF»: программа вынимает изображения таблиц приложения А, определяет номера по подписям и строит жёлтые варианты по перечню стандарта; номера можно исправить до записи ([docs/sign-catalog.md](docs/sign-catalog.md)). Прежний способ — архив ZIP с документом из библиотеки или кодом и редакцией, введёнными вручную. Перед записью приложение перечисляет новые и исключаемые коды, знаки, у которых сменилась только редакция источника, и показывает изменённые изображения рядом с текущими. При загрузке ZIP PDF можно приложить только для записи хеша источника. После подтверждения новая редакция становится текущей, прежние PNG сохраняются в истории локальной SQLite, а отсутствующие в новом архиве коды больше не доступны новым стойкам. На этапе «Знаки и объекты» после применения правок нажмите «Закрепить редакции PNG» и сохраните проект: схема v6 запишет версии использованных изображений и сможет открывать исторические PNG из той же локальной базы. После изменения состава знаков закрепите редакции заново. Старые проекты без закрепления используют активный каталог; для переноса проекта с закреплением на другой компьютер необходима также локальная база с историей знаков.

Для пакетного импорта через CLI остановите приложение и выполните предварительный просмотр и импорт:

```bash
npm run import:pu66 -- "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:pu66 -- --apply "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:signs -- "local-input/signs.zip"
npm run import:signs -- --apply "local-input/signs.zip"
```

Запуск команды без `--apply` только сообщает количество новых и изменённых записей. `--apply` сохраняет их с резервной копией; повторная загрузка того же файла не создаёт новую редакцию. CLI знаков работает только с ZIP и помечает редакцию ГОСТ как неизвестную; для печати загрузите каталог через интерфейс (из PDF библиотеки или ZIP с указанием редакции). Оригинал каждой ПУ-66 и полная извлечённая таблица остаются только в SQLite. Локальный интерфейс показывает краткую сводку; отдельный API для будущего листа выдаёт лишь место, осевую подпись, название дороги и ширину проезжей части. После фактической сверки линейным подразделением откройте «Реестры» → «Импорт Excel и знаков» и запишите дату и ответственного для конкретной редакции. Сверка проводится 30 января каждого года; импорт Excel сам по себе не фиксирует её проведение, новая редакция требует отдельной записи. Запись о сверке остаётся в локальной базе и не включается в экспорт проекта. Знаки хранятся как две версии PNG (с номером и без; для знаков из PDF они совпадают). Ранее созданные автоматической трассировкой SVG удаляются при обновлении локальной базы. См. [инструкцию проверки](TESTING.MD) и [каталог знаков](docs/sign-catalog.md).

В «Проекты» → «Новый проект» найдите переезд в локальном реестре ПУ-66 по километру и пикету («53 км 2 пк», «53/2»), станции, участку или дороге: форма покажет место, подпись оси, дорогу и ширину, которые будут закреплены в проекте, а идентификатор подставится из карточки. Кнопка «Создать проект» доступна только после выбора карточки; если реестр пуст или недоступен, форма сообщает, что начать новый проект невозможно, и предлагает импортировать ПУ-66. Затем введите длины фронта, отвода, буфера и три скорости. Размеры незадействованного варианта остаются пустыми. На этапе «Исходные данные» можно найти другую карточку тем же поиском, сравнить поля с проектом и явно закрепить редакцию; это не подтверждает актуальность карточки. На этапе «Схема движения» уточняются размеры и параметры, на этапе «Знаки и объекты» работают поле, палитра и кнопка условной сборки шаблона после выбора условий на этапе 2. На этапе «Проверка и лист» видны пустые поля, отличия размерной цепочки от рисунка ОДМ и пункты ручной сверки, затем доступен полноразмерный черновой лист, кнопки «Печать черновика A4» и «Скачать PNG» (около 300 dpi). После отметки «Я проверил лист…» лист печатается и выгружается как выпускной — без отметки «черновик» и служебных строк (строка с источником схемы — ОДМ 218.6.019-2016, приложение Б, рис. Б.33/Б.34 — остаётся); отметка сбрасывается при любом изменении проекта и не заменяет согласование. При замечаниях, блокирующих печать, Ctrl+P печатает вместо листа их список. Уменьшенный лист справа обновляется после применения правок. Отсутствие замечаний не означает соответствия нормам. Печатайте только для внутренней сверки: фактическая геометрия, нормативная расстановка и применимость ещё не подтверждены. Лист не берёт исходный JSON или полную карточку ПУ-66, но содержит отобранные конфиденциальные сведения; защищайте распечатки и файлы PDF. Старые v1–v5 и редакции SQLite открываются с преобразованием в v6 без переписывания исходных снимков. Примените правки, сохраните локально или скачайте JSON v6 через «Действия с проектом»; обновление реестра ПУ-66 не меняет сохранённый проект автоматически.

### Исполняемый файл для Windows

Для работы без установки Node.js соберите переносной файл командой `npm run build:exe`. Сборка работает на Windows и Linux: интерфейс из `dist/` встраивается в копию `node.exe` той же версии Node.js (Node.js single executable application). Результат — один файл `release/editor-of-tod.exe` размером около 90 МБ; права администратора не нужны. Рабочий процесс «Windows exe» в GitHub Actions запускается только вручную (Actions → «Windows exe» → Run workflow): собирает тот же файл на Windows, прогоняет на нём браузерные сценарии и сохраняет его как артефакт этого запуска на 14 дней. Автоматической сборки и публикации нет.

Скопируйте файл в отдельную папку, например `Документы\Редактор ОДД\`, и запустите двойным щелчком. Откроется окно консоли и браузер с адресом `http://127.0.0.1:4100/`. Данные создаются в `private-data\` рядом с программой, поэтому папку можно перенести целиком. Если в папку программы нельзя записывать, используется `%LOCALAPPDATA%\editor-of-tod\private-data\`. Путь выводится в окне консоли. Закрытие окна консоли останавливает редактор. Повторный запуск при уже работающем редакторе только открывает браузер. Если порт занят другой программой, задайте другой: `set TOD_PORT=4101` и запуск из той же командной строки. `TOD_DATABASE_PATH` задаёт путь к базе явно, `--no-browser` запускает без открытия браузера.

Файл не подписан, поэтому SmartScreen может показать предупреждение «Windows защитила ваш компьютер» → «Подробнее» → «Выполнить в любом случае». Встраивание нарушает подпись исходного `node.exe` — это ожидаемо. Требования: Windows 10/11 x64, современный браузер (Edge или Chrome), около 150 МБ на диске плюс размер базы.

Версии зависимостей зафиксированы в `package-lock.json`; CI выполняет `npm ci` и `npm run check` на Linux с Node 24 и на Windows с Node 26, а также браузерные сценарии Chromium на Linux. Проверка прямого запуска API использует только временную SQLite в памяти и не открывает рабочую базу. Автоматическая публикация отсутствует: даже после сборки схема не считается проверенной или согласованной.

## Структура и процесс

- `src/domain/` — модель и JSON v1–v6, создание проекта, привязка и поиск ПУ-66, условная сборка шаблона, рисование листа (`sheet-drawing.ts`), проверки заполнения, подсказка способа пропуска, нормативные документы и параметры, разбор графы «Норма» ПУ-66, история действий.
- `src/App.vue` — пошаговая навигация и постоянный предпросмотр листа; `src/composables/useProjectSession.ts` управляет открытым проектом, правками, историей и локальным сохранением, `useNormativeRules.ts` — подтверждёнными нормативными параметрами.
- `src/components/` — формы параметров и объектов, рабочая область, лист A4 и его PNG, реестры ПУ-66, каталог знаков из PDF и ZIP, библиотека нормативных документов, нормативные параметры, сведения ПУ-66 для нормативов.
- `server/` — локальный API и SQLite (миграции до версии 11), импорт XLSX и ZIP, извлечение знаков и текста из PDF (`sign-pdf.ts`, `pdf-text.ts`), нормативные параметры, точка входа exe (`desktop.ts`); конфиденциальные данные остаются в `private-data/`.
- `docs/scheme-format.md` — контракт нового файла и ограничения текущего импорта.
- `docs/migration.md` — инвентаризация автономного редактора и требования к совместимости.
- `docs/architecture.md` — текущие модули, хранение данных и направление развития.
- `docs/standards.md` — нормативные источники, параметры и порядок их подтверждения.
- `docs/pu66-data.md` — локальный реестр ПУ-66, выборки для схемы и нормативов, порядок актуализации.
- `docs/reference-schemes.md` — состав полей листов Б.33/Б.34 по предоставленным образцам и вопросы предметной сверки.
- `docs/sign-catalog.md` — каталог знаков из PDF ГОСТ Р 52290 и ZIP, история изображений и закрепление в проекте.
- [`ROADMAP.md`](ROADMAP.md) — очередность работ и критерии готовности.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — правила кода, проверок и изменений.
- [`TESTING.MD`](TESTING.MD) — локальный запуск и проверка импорта на обезличенном примере.
- `src/help/help-content.ts` — текст встроенной справки для составителя.
- [учебные листы Б.33/Б.34](tests/fixtures/review-b33-v4.json) — два вымышленных JSON v4 для визуальной проверки компоновки; [Б.34](tests/fixtures/review-b34-v4.json) содержит ручных регулировщиков.
- [шаблон PR](.github/PULL_REQUEST_TEMPLATE.md) — что приложить к ревью.
- [`CHANGELOG.md`](CHANGELOG.md) — история изменений репозитория.

Изменения вносятся через ветку и pull request. Для шаблонов, знаков, расстояний и экспортируемого листа к PR прикладываются проверяемые примеры и ссылка на конкретную редакцию источника. Предметную корректность схемы оценивает ответственный специалист перед передачей на согласование.

## Данные и права

Исходный HTML содержит встроенные записи из карточек ПУ-66, изображения знаков и реквизиты организации. Исходные PDF стандартов и руководство пользователя также предоставлены для анализа. Эти материалы **не входят** в открытый репозиторий и **не подпадают** под его лицензию MIT. Перед публикацией любого набора переездов, изображения, полного текста стандарта или исходного прототипа отдельно проверяются права и допустимость раскрытия. Для локальных материалов предусмотрены игнорируемые каталоги `local-input/` и `private-data/`.

Импорт JSON проверяет структуру файла, сохраняет исходный v1 JSON внутри новой копии, показывает перенесённые поля и предупреждения. Импортированный JSON не забирает карточку ПУ-66 автоматически. При явной привязке и при создании нового проекта из карточки JSON-копия и черновик содержат выбранные сведения из карточки; обращайтесь с ними как с конфиденциальными данными и не помещайте в GitHub. До сохранения проект находится в памяти браузера; при сохранении копия отправляется локальному API на `127.0.0.1` и записывается в SQLite. База не синхронизируется с GitHub. Приложение подсказывает решения по подтверждённым нормативным параметрам, но не проверяет соответствие схемы нормативам в целом и не заменяет установленный порядок согласования.
