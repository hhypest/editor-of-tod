# Правила разработки

Репозиторий открыт для изменений через pull request. Приоритеты: сохранность проектов пользователя, проверяемость схем и ясное происхождение нормативных и справочных данных.

## Рабочий цикл

1. Создайте ветку от `main`: `feat/…`, `fix/…`, `docs/…` или `chore/…`.
2. Сформулируйте пользовательское поведение и критерии проверки до изменения шаблонов или расчётов. Для геометрии и импорта подготовьте обезличенные примеры.
3. Сделайте ограниченное по смыслу изменение. Если меняется формат JSON, добавьте миграцию и проверку совместимости.
4. Выполните `npm ci` (при первом запуске) и `npm run check`; для предметных функций добавьте необходимые тесты.
5. Обновите README, TESTING.MD, дорожную карту и changelog, если изменились возможности, ограничения или шаги проверки. Если изменилось поведение для составителя, обновите встроенную справку `src/help/help-content.ts`: подписи кнопок и полей в ней размечены как `[[Подпись]]`, и тест не пропустит подпись, которой нет в интерфейсе. Заполните [шаблон PR](.github/PULL_REQUEST_TEMPLATE.md).
6. Не объединяйте PR с изменениями шаблонов и нормативной логики без предметной проверки ответственного специалиста и зафиксированной редакции источника.

Заголовки коммитов — короткие, в повелительном или описательном стиле, например `feat: add versioned scheme import` или `docs: clarify approval workflow`. Один PR описывает один результат; промежуточные технические шаги допустимы внутри него.

## TypeScript и Vue

- Используйте Vue Single-File Components и Composition API; новая логика пишется на TypeScript. Не отключайте строгие проверки типов и `noUncheckedIndexedAccess` ради обхода ошибки.
- Предметные расчёты, формат проекта, правила шаблонов и валидация должны жить вне компонентов и не обращаться к DOM. Компоненты отвечают за ввод и отображение.
- Различайте метры, координаты листа, идентификаторы знаков и текстовые подписи в типах и названиях переменных. Не выводите физические размеры из условного масштаба картинки.
- Каждая схема хранит версию формата и ссылку на источник шаблона. Числа нормативных правил не записываются в код как «истина»: они описываются в `src/domain/normative-parameters.ts` с документом и пунктом и подтверждаются составителем в локальной SQLite ([docs/standards.md](docs/standards.md)); значение прототипа действует только до подтверждения. Импортируемый JSON валидируется на границе; ошибка сообщает, какое поле не удалось прочитать. Оригинал файла не перезаписывается автоматически.
- Для пользовательского текста применяйте безопасное текстовое отображение Vue. Не вставляйте неочищенный ввод через `v-html`, `innerHTML` или атрибуты SVG.
- Данные реестра переездов не зашиваются в UI. Разработку и CI ведите на обезличенных фикстурах; реальные сведения загружаются только после определения прав и политики доступа.
- Не добавляйте полные тексты ГОСТ, сканы, изображения или иные сторонние активы без прав на публикацию и отдельного учёта происхождения.

Текущие настройки ESLint, Oxlint и Prettier определяют синтаксис и форматирование. Перед PR запустите `npm run format` и `npm run check`. Проверка `check:public` отклоняет отслеживаемые Git файлы xlsx, sqlite, zip, png, jpg и pdf; для тестов собирайте вымышленные книги и PDF программно (`scripts/generate-pu66-samples.ts`, `server/__tests__/pdf-fixture.ts`). Скрипт `lint` только проверяет и не исправляет файлы; для исправления используйте `npm run lint:fix`.

## Проверки предметной логики

Проверки добавляются вместе с переносом функций, а не ради покрытия пустого каркаса. Для шаблонов нужны примеры обеих сторон движения и условий применения, включая границу 30 м; для импорта — старые JSON-файлы без персональных данных; для печати — просмотр PDF/PNG и отсутствие обрезанных подписей. Изменение правила требует ссылки на пункт и редакцию документа. Автоматическая проверка не заменяет инженерного решения составителя.

## Ревью и выпуск

PR должен объяснять, что изменилось, почему, на каких примерах проверено, влияет ли это на нормативные параметры, права на данные, печатный лист и старые проекты. Для интерфейса приложите изображение, если оно помогает сравнить результат. Если проверка не выполнена, укажите причину и остающийся риск в описании PR. Не отмечайте функцию как завершённую в README и changelog до её фактической реализации.
