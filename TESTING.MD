# Локальное тестирование

Руководство для проверки Vue-приложения на домашнем компьютере. Можно создать проект без прежнего файла, открыть JSON v1/v2/v3/v4/v5, править параметры и объекты, закрепить ограниченные поля локальной ПУ-66, сохранить черновик в SQLite или скачать копию `schemaVersion: 5`. Условный черновой лист A4 можно распечатать через браузер для внутренней сверки. Реестры ПУ-66 и знаков остаются на компьютере составителя. Автосохранение, полный нормативный лист СОДД, отдельный экспорт PDF/PNG и согласование ещё не реализованы.

**Docker не нужен:** локальный сервер и SQLite запускаются вместе с приложением через Node.js. Нужны Node.js, npm и браузер; `compose.yml` не требуется.

Перед обновлением существующей базы сохраните копию `private-data/registry.sqlite` вместе с каталогом `private-data/backups/` в разрешённом месте. Новая SQLite версии 7 не переписывает прежние редакции черновиков; новые записи с исходным v1 JSON используют общий текст по SHA-256. Сохраните черновик после открытия прежнего проекта, перезапустите приложение, откройте редакции из истории и скачайте JSON v5: поле `source.originalJson` должно остаться полным.

Копии не удаляются автоматически. Для проверки накопившихся файлов выполните `npm run backups:prune` без аргументов: увидите список копий к удалению при пороге 20 штук и 90 дней. Настройте пороги `-- --keep 30 --max-age-days 180`; если список согласован с правилами хранения, повторите команду с `--apply`. Минимум одна копия сохраняется даже после истечения срока. Проверка не затрагивает файлы с другими именами. Не применяйте очистку, пока необходимые версии не помещены в архив организации.

## Подготовка

- Установите Git, Node.js 24 (не ниже 24.12.0) либо Node.js 26 (не ниже 26.7.0) и npm. В `.nvmrc` указана версия 24 для обычного запуска; проверить установленную версию можно командами `node --version` и `npm --version`.
- Откройте терминал (в Windows — PowerShell) и выполните команды ниже. Для первого запуска:

```bash
git clone https://github.com/hhypest/editor-of-tod.git
cd editor-of-tod
node --version
npm --version
npm ci
npm run dev
```

Если репозиторий уже скачан, откройте его каталог и перед проверкой выполните `git pull --ff-only`, затем `npm ci` и `npm run dev`. Откройте `http://127.0.0.1:5173/`: интерфейс работает на порту 5173, локальный API на 4100. Терминал с обоими процессами оставьте открытым; для остановки нажмите `Ctrl+C`. Первый `npm ci` скачивает зависимости из npm.

Открывайте приложение через адрес Vite, а не двойным щелчком по `index.html`. Запуск не требует проброса портов, учётной записи или внешней БД. Приложение слушает только `127.0.0.1`; другая машина в сети не получает к нему доступ. SQLite создаётся автоматически в `private-data/registry.sqlite` и остаётся на вашем компьютере. База и копии **не зашифрованы**: ограничьте доступ к ним средствами ОС и не помещайте реальные карточки в облачную синхронизацию без разрешения на такое хранение.

### Первый запуск с пустой базой

Для воспроизводимого опыта используйте новый каталог проекта, где ещё нет `private-data/registry.sqlite`. Не удаляйте рабочую базу ради теста. После `npm ci` выполните в PowerShell:

```powershell
npm run samples:pu66
npm run dev
```

Откройте `http://127.0.0.1:5173/`. В `private-data/` автоматически появится `registry.sqlite`; на странице «Проекты» откроется подсказка с двумя задачами: знаки и ПУ-66. Нормативный реестр уже содержит четыре краткие записи, а список импортированных карточек и знаков пуст. Пять учебных файлов `PU66-DEMO-101.xlsx`—`PU66-DEMO-104.xlsx` и `PU66-DEMO-STATION-105.xlsx` созданы в `local-input/examples-pu66/`; они полностью вымышлены, хотя координаты полей соответствуют предоставленным формам. Повторный запуск сохраняет существующие файлы и создаёт только отсутствующие, например станционный пример после обновления проекта.

1. Нажмите **«Импортировать ZIP знаков»**. В блоке каталога укажите `ГОСТ Р 52290-2024` и редакцию `2024`, выберите предоставленный вами ZIP с каталогами `PNG с номером/` и `PNG без номера/`. PDF для записи хеша необязателен. Нажмите **«Просмотреть изменения знаков»**: ожидается 420 знаков для ранее предоставленного архива. Проверьте источник и нажмите **«Подтвердить каталог и создать копию SQLite»**. После возврата к «Проектам» подсказка покажет, что знаки уже в базе.
2. Нажмите **«Импортировать ПУ-66»**. Выберите сразу четыре XLSX из `local-input/examples-pu66/` и нажмите **«Просмотреть изменения»**. Ожидается четыре новые карточки с ключами `90001:12:3`, `90002:24:7`, `90003:36:1`, `90004:48:5`. Нажмите **«Подтвердить импорт и создать копию SQLite»**. Списки содержат четыре карточки; повторный просмотр тех же файлов показывает четыре неизменённые карточки. Импортируйте отдельным пакетом `PU66-DEMO-STATION-105.xlsx`: участок пуст, станция заполнена, ключ `ст.Условная станция Озёрная:53:2:к905`. Можно также выбрать все пять книг одним пакетом: создаётся одна резервная копия. Подсказка первоначальной настройки на странице «Проекты» больше не показывается.
3. Остановите приложение `Ctrl+C`, снова выполните `npm run dev`. Пять учебных карточек и каталог знаков остаются в базе; файлы `private-data/registry.sqlite` и `private-data/backups/` не добавляются в Git. Дата ежегодной сверки у учебных карточек **не появляется**: её следует записывать только после реальной сверки, проводимой линейным подразделением 30 января.

Порядок двух импортов не влияет на создание базы; каждая операция требует отдельного предварительного просмотра и подтверждения. Если у вас уже есть рабочая SQLite, учебные книги импортируются в неё как отдельные записи. Для изолированной проверки используйте новый каталог или отдельную копию проекта.

## Автоматические проверки

В другом терминале из каталога репозитория выполните:

```bash
npm run check
```

Команда последовательно проверяет форматирование, Oxlint, ESLint, типы TypeScript, прямой запуск локального API/CLI через Node.js с временной SQLite в памяти, тесты Vitest и сборку Vite. Ожидается код завершения `0`, все тесты проходят, сборка сообщает об успешном создании `dist/`. Отдельно проверку запуска можно выполнить командой `npm run check:runtime`, тесты — `npm run test`. Для браузерного smoke установите Chromium командой `npx playwright install chromium` и выполните `npm run test:e2e`; тест запускает отдельную временную SQLite и не открывает вашу рабочую базу.

Остановите `npm run dev` и при необходимости проверьте собранную версию:

```bash
npm run build
npm run preview
```

Откройте `http://127.0.0.1:4173/` и повторите сценарии ниже. `preview` запускает и API, и просмотр сборки; он ничего не публикует. Для запуска собранного приложения через один локальный адрес выполните `npm run build`, затем `npm run local` и откройте `http://127.0.0.1:4100/`.

### Проверка исполняемого файла Windows

1. Выполните `npm run build:exe`. Ожидается `release/editor-of-tod.exe` и строка с SHA-256. На Linux можно собрать файл для текущей системы командой `npm run package:exe -- --target host` (после `npm run build-only`).
2. Браузерные сценарии на собранном файле: `TOD_E2E_EXE=release/editor-of-tod.exe npm run test:e2e` (в PowerShell: `$env:TOD_E2E_EXE="release\editor-of-tod.exe"; npm run test:e2e`). Тест использует временную SQLite.
3. Скопируйте файл в пустую папку и запустите двойным щелчком. Открывается браузер, в консоли указан путь `private-data\registry.sqlite` рядом с программой, на странице «Проекты» видна подсказка первого запуска.
4. Запустите файл второй раз: второе окно сообщает, что редактор уже запущен, открывает браузер и закрывается.
5. Закройте окно консоли первого экземпляра: страница перестаёт отвечать, файл базы можно скопировать. После повторного запуска данные на месте.
6. Запустите `set TOD_PORT=70000` и затем программу из той же консоли: ожидается понятная ошибка о неверном порте, окно ждёт нажатия Enter.

## Проверка пошагового интерфейса

1. На первом экране «Проекты» переключите «Новый проект», «Черновики SQLite», «Открыть JSON». В каждой вкладке показана только выбранная задача; поля незавершённой формы создания остаются при переключении вкладок.
2. Создайте вымышленный проект или откройте `tests/fixtures/manual-v1.json` через «Открыть JSON». Слева появятся четыре этапа, справа — уменьшенный черновой лист с текущим вариантом. Нажатие «Открыть лист A4 и печать» переводит на четвёртый этап.
3. На «Исходных данных» измените участок, **не применяя** ввод, перейдите на «Схему движения» и вернитесь. Введённый текст остаётся в форме; сверху видна пометка о неприменённом вводе, сохранение и печать недоступны. Нажмите «Отменить ввод» или «Применить правки».
4. На «Схеме движения» проверьте размеры и предварительный вариант, на «Знаки и объекты» — поле и свойства. Добавьте стойку со знаком из локального ZIP, примените правки и нажмите «Закрепить редакции PNG»; после сохранения JSON в `signImages.revisions` появится номер редакции кода, а в `signImages.catalog` — источник. При повторном импорте изменённого ZIP прежний проект показывает старое изображение, пока в SQLite есть история; новая стойка берёт активное. На «Проверке и листе» откройте пункт замечания кнопкой «Перейти»: приложение переводит к соответствующей форме и ставит курсор в первое незаполненное поле (например, «Участок» для «Места работ» или «Должность» для утверждения владельцем дороги). Если на этапе «Знаки и объекты» осталась неприменённая правка объекта, «Перейти» открывает этот этап и сообщает, что правку нужно применить или отменить. Кнопка «Печать черновика A4» находится над большим листом на четвёртом этапе, рядом с «Обновить PNG».
5. Нажмите «Реестры». «Импорт Excel и знаков» и «Карточки и нормативы» переключаются отдельно; возврат к проекту через этап слева не сбрасывает открытый проект.

Этот сценарий относится к «Реестры» → «Карточки и нормативы». Импортированные XLSX находятся в соседней вкладке «Импорт Excel и знаков» и не изменяют ручной список.

## Импорт XLSX ПУ-66 и архива знаков

Для импорта ПУ-66 через интерфейс оставьте `npm run dev` или `npm run local` запущенным. В «Реестры» → «Импорт Excel и знаков» выберите от одного до 100 разрешённых XLSX размером до 4 МБ каждый и не более 40 МБ в сумме и нажмите «Просмотреть изменения». Браузер передаст книги только локальному API; предварительный просмотр не записывает их в SQLite. Проверьте для каждой карточки место, название дороги и действие «новая», «обновление» или «без изменений». Нажмите «Подтвердить импорт и создать копию SQLite»: после записи появится число изменённых карточек и имя резервной копии. Повторный просмотр тех же файлов должен показывать только неизменённые карточки, а кнопка подтверждения будет неактивной. Если база изменилась после просмотра, запись отклоняется: нажмите «Просмотреть изменения» заново. Не публикуйте скриншоты с данными ПУ-66.

Архив знаков можно обновить прямо в интерфейсе: в том же блоке укажите документ и редакцию ГОСТ, выберите ZIP (до 32 МБ), при желании приложите PDF (до 10 МБ), затем отдельно просмотрите план и подтвердите импорт. PDF хранится только как хеш; приложение не проверяет по нему рисунки. После записи должен отображаться источник, число активных знаков и результат сравнения. Повтор того же набора показывает «без изменений». Для предоставленного ZIP ожидается 420 знаков. Если новый архив не содержит какой-либо код, он исключается из активного каталога, но остаётся в локальной истории SQLite. Код `3.24_50` из образцов в предоставленном архиве отсутствует; программа не создаёт его замену.

Для больших пакетов через CLI остановите `npm run dev` или `npm run local`. Поместите разрешённые XLSX и ZIP в каталог `local-input/` (он исключён из Git) либо передайте абсолютные пути. Не переименовывайте содержимое ZIP. В приведённых командах замените имена файлов на свои:

```bash
npm run import:pu66 -- "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:pu66 -- --apply "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:signs -- "local-input/signs.zip"
npm run import:signs -- --apply "local-input/signs.zip"
```

Без `--apply` команды только показывают количество новых, изменённых и неизменённых записей. С `--apply` каждая команда сперва создаёт копию в `private-data/backups/`, затем записывает пакет целиком. Повторите просмотр: те же файлы должны показывать только неизменённые записи. После запуска приложения нажмите «Обновить каталоги». Для предоставленных четырёх XLSX и ZIP ожидаются 4 карточки и 420 знаков. Исходные XLSX сохраняются внутри локальной SQLite; исходный ZIP целиком не сохраняется, но сохраняются обе версии PNG каждого знака. Оба способа импорта ПУ-66 используют один парсер и одну базу; не загружайте один и тот же пакет дважды ради сравнения интерфейса и CLI.

При первом запуске новой версии существующая SQLite-база обновляется до версии 6: для старых баз версии 2 поле с автоматически трассированными SVG удаляется, файл уплотняется, затем создаются таблицы черновиков; база версии 3 получает таблицы черновиков, а базы версий 0–4 — журнал сверок импортированных карточек. Перед обновлением остановите приложение и сохраните копию `private-data/registry.sqlite` отдельно. Для уплотнения базы версии 2 нужно свободное место на диске. Старые резервные копии сохраняют своё содержимое. Версия 6 хранит историю PNG знаков с редакциями источника, полные снимки сохранённых проектов с исходным JSON и записи сверки; защищайте резервные копии так же, как основную базу. Старый импорт не становится «выверенным» после миграции: отметку вносит ответственный после фактической сверки.

Если скачана готовая приватная база, распакуйте `registry.sqlite` в `private-data/` **при остановленном приложении**, предварительно сохранив свою прежнюю базу и резервные копии. Затем запустите `npm run dev`. База содержит конфиденциальные данные, не шифруется приложением и не должна попадать в Git, публичные обращения или общий диск без разрешения.

Проверьте поиск по коду знака в каталоге и отображение PNG. Для вымышленного JSON из раздела ниже список использованных кодов сообщает, какие изображения доступны. Для карточки локальный экран показывает сводку составителю, а `/api/pu66/{ключ}/scheme` выдаёт только внутренний ключ, место, подпись оси, название дороги, ширину проезжей части, номер и время обновления редакции. Полный XLSX и техническая таблица через этот адрес не выдаются.

Для проверки журнала сверок используйте только разрешённую карточку и не переносите её сведения в отчёт. ## Проверка своего старого проекта

Экспортируйте JSON из автономного редактора и сохраните резервную копию до теста. Ключ `localStorage` старого HTML-прототипа напрямую этим приложением не читается: нужен именно сохранённый JSON-файл. Личные или служебные проекты храните в локальном каталоге `local-input/` или `private-data/` (оба исключены из Git), не добавляйте их в PR и публичные обращения.

Загрузите копию файла, прочитайте предупреждения, сохраните локальный черновик при необходимости, скачайте v5 и отдельно исходный JSON. Сопоставьте число объектов, номера знаков, реквизиты и значимые ручные правки с оригиналом. Сохранение v5 или черновика не заменяет исходный файл. Координатная область и черновой лист показывают только условную дорогу и размерную цепочку; они не строят полноценную схему СОДД, поэтому соответствие реальным условиям и нормативам необходимо проверять отдельно.

## Если что-то не работает

- `npm ci` показывает `EBADENGINE` с Node 26.7.0: обновите репозиторий командой `git pull --ff-only`, затем выполните `npm ci` снова. Начиная с исправления прямого запуска поддерживаются Node 24.12+ и 26.7+ в пределах соответствующих основных версий. Предупреждения `deprecated` для косвенных зависимостей сами по себе не останавливают установку.
- `npm run dev` сообщает `ERR_MODULE_NOT_FOUND` для `src/domain/model`: проверьте, что обновились `src/domain/local-projects.ts` и `src/domain/model.ts`, запустите `npm run check:runtime`. Эта проверка должна пройти до запуска интерфейса и не обращается к вашей рабочей SQLite.
- `node` или `npm` не распознаётся: завершите установку поддерживаемой версии Node.js и откройте новый терминал; проверьте `node --version`.
- `npm ci` сообщает о несовпадении `package.json` и lockfile: убедитесь, что вы на актуальной ветке `main` и локально не меняли эти файлы. Для теста используйте чистый клон.
- Страница не открывается: откройте `http://127.0.0.1:5173/` и проверьте, что оба процесса запущены. Порты 4100 и 5173 фиксированы: если один из них занят, остановите программу, занявшую порт, и повторите запуск. Для `preview` нужен свободный порт 4173.
- Блок реестров показывает ошибку: проверьте вывод локального API в терминале и наличие прав на запись в `private-data/`. Не прикладывайте файл базы к публичному обращению.
- Импорт не проходит: убедитесь, что выбран JSON проекта с `v: 1` или `schemaVersion: 2/3/4`, а не HTML-файл прототипа. Сверьте поле из сообщения об ошибке и проверьте исправный пример из репозитория.

При сообщении об ошибке полезно записать ОС, браузер, версии Node и npm, SHA коммита (`git rev-parse --short HEAD`), шаги воспроизведения, ожидаемый и фактический результат. Для публичного отчёта используйте обезличенный пример; не прикладывайте реальные карточки переездов, персональные данные и служебные файлы.
