## РК1: надёжность перед приёмкой (05.10.2026)

Проверяется на новой сборке exe с копией рабочей папки. Перед началом скопируйте всю папку программы вместе с `private-data` в отдельное место.

1. **Копия перед обновлением базы.** Запустите новую сборку в папке, где раньше работала прежняя. В окне запуска есть строка «База обновлена: версия N → 13. Прежняя база сохранена: …». В `private-data\backups` появился файл `registry-before-update-vN-….sqlite`. Проекты, карточки ПУ-66, документы и подтверждения параметров на месте. При повторном запуске строки об обновлении и новой копии нет.
2. **Возврат к прежней сборке.** Закройте программу, положите файл `registry-before-update-…` на место `private-data\registry.sqlite` (в копии папки) и запустите прежнюю сборку: она открывает базу с данными на момент обновления.
3. **Повторный запуск.** Не закрывая программу, запустите exe ещё раз: второе окно сообщает «Эта база уже открыта», открывает тот же адрес и закрывается. В `private-data` на время работы есть файл `registry.sqlite.instance.json`; после закрытия окна программы он исчезает.
4. **Папка через сетевое имя** (если программа лежит на сетевом диске). Запустите exe через букву диска, затем второй раз — через путь вида `\\сервер\папка\…`: второе окно сообщает, что база уже открыта, и не запускает вторую программу.
5. **Прежняя сборка рядом.** Запустите сборку, выпущенную до 02.10.2026, затем новую: новая сообщает, что на порту работает прежняя сборка, и просит закрыть её окно. После закрытия прежней новая запускается.
6. **Выпуск без условий работ.** В проекте с двумя регулировщиками оставьте на этапе 2 «Время суток» неуказанным, отметьте все пункты проверки: флажок «Я проверил лист» на этапе 4 недоступен, под ним причина «Выпуск недоступен: Укажите на этапе 2, выполняются ли работы только в светлое время суток». После выбора значения лист выпускается, в примечаниях нет слова «уточнить».
7. **Вид документа каталога.** В «Реестры» → «Нормативные документы» попробуйте сменить вид стандарта, по которому загружен каталог знаков: сохранение отклоняется с сообщением «вид документа изменить нельзя». Примечание к тому же документу сохраняется.

Перед изменением схемы программа сама сохраняет прежнюю базу в `private-data/backups/registry-before-update-v<версия>-<время>.sqlite` и сообщает имя файла в окне запуска; если копию записать не удалось, база не обновляется. SQLite версии 7 и выше не переписывает прежние редакции черновиков; новые записи с исходным v1 JSON используют общий текст по SHA-256. Сохраните черновик после открытия прежнего проекта, перезапустите приложение, откройте редакции из истории и скачайте файл проекта: поле `source.originalJson` должно остаться полным.

Копии не удаляются автоматически. Для проверки накопившихся файлов выполните `npm run backups:prune` без аргументов: увидите список копий к удалению при пороге 20 штук и 90 дней. Настройте пороги `-- --keep 30 --max-age-days 180`; если список согласован с правилами хранения, повторите команду с `--apply`. Минимум одна копия сохраняется даже после истечения срока. Проверка не затрагивает файлы с другими именами, в том числе копии `registry-before-update-…`, снятые перед обновлением базы: их удаляют вручную, когда возврат к прежней сборке больше не нужен. Не применяйте очистку, пока необходимые версии не помещены в архив организации.

Неизвестное условие и специальное разрешение допускают ручное число с обоснованием; автомагистраль видна справочно, но применить её как условие переезда нельзя.

### Приёмка исключения ПУ-66 (вечерняя проверка)

Функция находится в ветке `feat/pu66-exclusion`; после её включения в `main` обычное обновление выше получает её автоматически. Для проверки PR отдельно:

```bash
git fetch origin
git switch feat/pu66-exclusion
npm ci
npm run samples:pu66
npm run dev
```

Используйте учебные карточки и отдельную базу. Перед первым запуском новой версии сохраните копию своей рабочей базы при остановленном редакторе: структура обновляется с v11 на v12, старая программа v12 не открывает. Не удаляйте рабочие данные ради тестирования.

1. Импортируйте учебные книги. Создайте и сохраните проект по `90001:12:3`.
2. В «Реестры» → «Карточки и нормативы» найдите эту карточку, отметьте её, укажите дату, составителя и причину. Для «Другая причина» пустое пояснение должно мешать просмотру. Укажите действующего преемника `90002:24:7`, просмотрите и подтвердите исключение. Проверьте создание файла в `private-data/backups/`.
3. В списке «Исключённые» проверьте дату, причину, составителя, преемника и историю. Новый проект и ежегодная сверка не должны предлагать исключённую карточку. Остальные карточки остаются доступными.
4. Откройте сохранённый проект. На этапе 1 должны остаться прежний ключ и снимок, появиться предупреждение и «Сравнить с преемником». Сравнение не меняет проект; применение новой привязки — отдельная кнопка. До применения проверьте отдельный пункт «Карточка ПУ-66 исключена» на этапе 4: для выпуска нужна его отметка.
5. Снова выберите исходный XLSX в импорте. План должен показать исключение. Без явного возврата карточка остаётся исключённой, даже при изменении книги. Для возврата поставьте отметку у карточки, укажите дату и составителя и повторите просмотр: только затем подтверждение доступно. Неизменённая книга также допускает явный возврат с копией базы.
6. Исключите карточку повторно и верните через список «Исключённые». История должна содержать все действия; прежняя отметка проверки исключения не подтверждает новое исключение. Перезапустите программу и проверьте сохранность карточек, истории и проекта.

Для обратной связи достаточно указать номер сценария, результат и обезличенный снимок интерфейса. Реальные книги, базы и резервные копии в GitHub не прикладывайте. Предметная проверка допустимости старой схемы после передачи/закрытия остаётся решением составителя; исключение в программе не выполняет процедуру закрытия переезда.

Проверка замечаний Codex к PR #71: у подготовленного выпускного листа вызов Ctrl+P выводит сообщение о необходимости кнопки «Печать листа A4», а эта кнопка заново проверяет статус. После завершения или отмены её диалога новый Ctrl+P опять требует подготовки. Если другой процесс поменял преемника или его редакцию, сравнение использует обновлённый статус, а устаревший план исключения отклоняется.

### Первый запуск с пустой базой

Для воспроизводимого опыта используйте новый каталог проекта, где ещё нет `private-data/registry.sqlite`. Не удаляйте рабочую базу ради теста. После `npm ci` выполните в PowerShell:

```powershell
npm run samples:pu66
npm run dev
```

Откройте `http://127.0.0.1:5173/`. В `private-data/` автоматически появится `registry.sqlite`; на странице «Проекты» откроется подсказка с двумя задачами: знаки и ПУ-66. Нормативный реестр уже содержит четыре краткие записи, а список импортированных карточек и знаков пуст. Пять учебных файлов `PU66-DEMO-101.xlsx`—`PU66-DEMO-104.xlsx` и `PU66-DEMO-STATION-105.xlsx` созданы в `local-input/examples-pu66/`; они полностью вымышлены, хотя координаты полей соответствуют предоставленным формам. Повторный запуск сохраняет существующие файлы и создаёт только отсутствующие, например станционный пример после обновления проекта.

1. Прикрепите PDF ГОСТ Р 52290 в «Реестры» → «Нормативные документы» (назначение «Изображения знаков»), затем в «Импорт Excel и знаков» нажмите **«Извлечь знаки из PDF»**, проверьте номера и нажмите **«Записать каталог знаков и создать копию SQLite»**: для ГОСТ Р 52290-2024 ожидается 395 знаков. Прежний способ: раскройте «Загрузка знаков из ZIP (прежний способ)»; если библиотека пуста, выберите «Не выбран» и укажите `ГОСТ Р 52290-2024` и редакцию `2024`; выберите ZIP с каталогами `PNG с номером/` и `PNG без номера/`, нажмите **«Просмотреть изменения знаков»** (420 знаков для ранее предоставленного архива) и **«Подтвердить каталог и создать копию SQLite»**. После возврата к «Проектам» подсказка покажет, что знаки уже в базе.
2. Нажмите **«Импортировать ПУ-66»**. Выберите сразу четыре XLSX из `local-input/examples-pu66/` и нажмите **«Просмотреть изменения»**. Ожидается четыре новые карточки с ключами `90001:12:3`, `90002:24:7`, `90003:36:1`, `90004:48:5`. Нажмите **«Подтвердить импорт и создать копию SQLite»**. Списки содержат четыре карточки; повторный просмотр тех же файлов показывает четыре неизменённые карточки. Импортируйте отдельным пакетом `PU66-DEMO-STATION-105.xlsx`: участок пуст, станция заполнена, ключ `ст.Условная станция Озёрная:53:2:к905`. Можно также выбрать все пять книг одним пакетом: создаётся одна резервная копия. Подсказка первоначальной настройки на странице «Проекты» больше не показывается.
3. Остановите приложение `Ctrl+C`, снова выполните `npm run dev`. Пять учебных карточек и каталог знаков остаются в базе; файлы `private-data/registry.sqlite` и `private-data/backups/` не добавляются в Git. Дата ежегодной сверки у учебных карточек **не появляется**: её следует записывать только после реальной сверки, проводимой линейным подразделением 30 января.

Порядок двух импортов не влияет на создание базы; каждая операция требует отдельного предварительного просмотра и подтверждения. Если у вас уже есть рабочая SQLite, учебные книги импортируются в неё как отдельные записи. Для изолированной проверки используйте новый каталог или отдельную копию проекта.

## Автоматические проверки

В другом терминале из каталога репозитория выполните:

```bash
npm run check
```

Команда последовательно проверяет, что Git не отслеживает рабочие книги, базы, архивы, PDF и изображения (`check:public`), затем форматирование, Oxlint, ESLint, типы TypeScript, прямой запуск локального API/CLI через Node.js с временной SQLite в памяти, тесты Vitest и сборку Vite. Ожидается код завершения `0`, все тесты проходят, сборка сообщает об успешном создании `dist/`. Отдельно проверку запуска можно выполнить командой `npm run check:runtime`, тесты — `npm run test`. Для браузерного smoke установите Chromium командой `npx playwright install chromium` и выполните `npm run test:e2e` (сценарии в `tests/e2e/*.spec.ts`: редактор, нормативные документы, ПДД, жизненный цикл ПУ-66, профиль переезда; список — `npx playwright test --list`); тест запускает отдельную временную SQLite и не открывает вашу рабочую базу. Откройте `http://127.0.0.1:4173/` и повторите сценарии ниже. `preview` запускает и API, и просмотр сборки; он ничего не публикует. Для запуска собранного приложения через один локальный адрес выполните `npm run build`, затем `npm run local` и откройте `http://127.0.0.1:4100/`.

Кнопка «Печать черновика A4» находится над большим листом на четвёртом этапе, рядом с «Обновить PNG».
5. Нажмите «Реестры». Вкладки «Импорт Excel и знаков», «Нормативные документы», «Нормативные параметры» и «Карточки и нормативы» переключаются отдельно; возврат к проекту через этап слева не сбрасывает открытый проект.

## Импорт XLSX ПУ-66 и архива знаков

Для импорта ПУ-66 через интерфейс оставьте `npm run dev` или `npm run local` запущенным. В «Реестры» → «Импорт Excel и знаков» выберите от одного до 100 разрешённых XLSX размером до 4 МБ каждый и не более 40 МБ в сумме и нажмите «Просмотреть изменения». Браузер передаст книги только локальному API; предварительный просмотр не записывает их в SQLite. Проверьте для каждой карточки место, название дороги и действие «новая», «обновление» или «без изменений». Нажмите «Подтвердить импорт и создать копию SQLite»: после записи появится число изменённых карточек и имя резервной копии. Повторный просмотр тех же файлов должен показывать только неизменённые карточки, а кнопка подтверждения будет неактивной. Если база изменилась после просмотра, запись отклоняется: нажмите «Просмотреть изменения» заново. Не публикуйте скриншоты с данными ПУ-66.

Справка: нажмите «Справка» в верхней панели на любом этапе или в реестрах — откроется раздел по текущему экрану (например, из «Нормативных параметров» — одноимённый раздел). Проверьте поиск («сверки 30 января» оставляет раздел о ПУ-66) и переход по оглавлению; при выборе раздела из оглавления поиск очищается.

Нормативные параметры: прикрепите PDF ОДМ 218.6.019-2016 и ГОСТ Р 52289-2019, откройте «Реестры» → «Нормативные параметры». Для каждого параметра из документа должна находиться цитата с номером страницы; для ваших документов предложенные значения — 250 авт/ч, 50 м, 500 авт/ч, 15 м, таблица 5, 20 км/ч. Для таблицы 1 ГОСТ Р 52289 (типоразмеры) цитата находится, но значения вводит или проверяет составитель; доля часа пик — решение составителя без цитаты. Введите «Кто подтверждает», подтвердите параметры и проверьте, что на этапе «Схема движения» Б.34 заголовок подсказки сменился на «по подтверждённым нормативным параметрам» и появилась кнопка выбора. Для доли часа пик и профиля переезда обязательно основание. Профиль переезда не подтверждается загрузкой ГОСТ: у него отдельная запись решения специалиста. В проекте из карточки ПУ-66 проверьте блок «Сведения ПУ-66 для нормативов»: кнопка «Подставить … авт/ч» заполняет интенсивность, вне населённого пункта кнопка «Выбрать типоразмер …» выставляет типоразмер (включая IV для дорог IА/IБ), расхождения с графой «Норма» (включая отличие от точного значения) выделены. Проверьте, что без введённой длины рабочей зоны подсказка не рекомендует знаки 2.6/2.7.

Знаки из PDF: в «Нормативных документах» добавьте PDF ГОСТ Р 52290 с назначением «Изображения знаков», затем в «Импорт Excel и знаков» нажмите «Извлечь знаки из PDF». Для ГОСТ Р 52290-2024 ожидается: страницы 25–67, 368 изображений, 395 знаков, 27 жёлтых вариантов по п. 3.2, ни одного изображения без номера. Проверьте отбор «Требуют проверки» (варианты 1.34.x, 5.15.x, 6.x), исправьте номер у любого изображения, нажмите «Проверить снова» и убедитесь, что запись недоступна до повторной проверки. Снимите номер у изображения (или получите изображение без номера): запись недоступна, пока номер не указан или не снята отметка «в каталог». После записи в «Текущем наборе» указан ГОСТ Р 52290, редакция 2024.

Прежний способ — ZIP. Раскройте «Загрузка знаков из ZIP (прежний способ)». Если в библиотеке есть PDF стандарта, он уже выбран в поле «Документ из библиотеки»; иначе выберите «Не выбран», укажите документ и редакцию ГОСТ и при желании приложите PDF (до 10 МБ) для хеша. Выберите ZIP (до 32 МБ), затем отдельно просмотрите план и подтвердите импорт. PDF хранится только как хеш; приложение не проверяет по нему рисунки. После записи должен отображаться источник, число активных знаков и результат сравнения. Повтор того же набора показывает «без изменений». Для предоставленного ZIP ожидается 420 знаков. Если новый архив не содержит какой-либо код, он исключается из активного каталога, но остаётся в локальной истории SQLite. Код `3.24_50` из образцов в предоставленном архиве отсутствует; программа не создаёт его замену.

Для больших пакетов через CLI остановите `npm run dev` или `npm run local`. Поместите разрешённые XLSX и ZIP в каталог `local-input/` (он исключён из Git) либо передайте абсолютные пути. Не переименовывайте содержимое ZIP. В приведённых командах замените имена файлов на свои:

```bash
npm run import:pu66 -- "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:pu66 -- --apply "local-input/card-1.xlsx" "local-input/card-2.xlsx"
npm run import:signs -- "local-input/signs.zip"
npm run import:signs -- --apply "local-input/signs.zip"
```

Без `--apply` команды только показывают количество новых, изменённых и неизменённых записей. С `--apply` каждая команда сперва создаёт копию в `private-data/backups/`, затем записывает пакет целиком. Повторите просмотр: те же файлы должны показывать только неизменённые записи. После запуска приложения нажмите «Обновить каталоги». Для предоставленных четырёх XLSX и ZIP ожидаются 4 карточки и 420 знаков. Исходные XLSX сохраняются внутри локальной SQLite; исходный ZIP целиком не сохраняется, но сохраняются обе версии PNG каждого знака. Оба способа импорта ПУ-66 используют один парсер и одну базу; не загружайте один и тот же пакет дважды ради сравнения интерфейса и CLI.

При первом запуске новой версии существующая SQLite-база обновляется до версии 13: для старых баз версии 2 поле с автоматически трассированными SVG удаляется, файл уплотняется, затем создаются таблицы черновиков; база версии 3 получает таблицы черновиков, а базы версий 0–4 — журнал сверок импортированных карточек. Перед обновлением программа сохраняет прежнюю базу в `private-data/backups/registry-before-update-v<версия>-…sqlite` (кроме баз версии 2: копия сохранила бы удаляемые векторные изображения) и печатает строку «База обновлена: версия N → 13. Прежняя база сохранена: …». Для уплотнения базы версии 2 нужно свободное место на диске. Старые резервные копии сохраняют своё содержимое. Далее: v7 — общий исходный JSON проектов по SHA-256, v8 — копии восстановления, v9 — раздельные ключи станционных карточек, v10 — библиотека нормативных документов и связь партии знаков с документом, v11 — текст страниц PDF и журнал подтверждений нормативных параметров, v12 — журнал исключения ПУ-66, v13 — владелец и срок активности копии восстановления. Для отката на прежнюю программу остановите приложение и положите эту копию на место `registry.sqlite`. База хранит историю PNG знаков, полные снимки проектов с исходным JSON, записи сверки и PDF стандартов; защищайте резервные копии так же, как основную базу. Старый импорт не становится «выверенным» после миграции: отметку вносит ответственный после фактической сверки.

Если скачана готовая приватная база, распакуйте `registry.sqlite` в `private-data/` **при остановленном приложении**, предварительно сохранив свою прежнюю базу и резервные копии. Затем запустите `npm run dev`. База содержит конфиденциальные данные, не шифруется приложением и не должна попадать в Git, публичные обращения или общий диск без разрешения.

Проверьте поиск по коду знака в каталоге и отображение PNG. Для вымышленного JSON из раздела ниже список использованных кодов сообщает, какие изображения доступны. Для карточки локальный экран показывает сводку составителю, а `/api/pu66/{ключ}/scheme` выдаёт только внутренний ключ, место, подпись оси, название дороги, ширину проезжей части, номер и время обновления редакции. Полный XLSX и техническая таблица через этот адрес не выдаются.

Для проверки журнала сверок используйте только разрешённую карточку и не переносите её сведения в отчёт. В «Реестры» → «Импорт Excel и знаков» выберите карточку, укажите фактическую дату сверки и подразделение или ответственного, затем запишите результат. После обновления страницы запись остаётся у этой редакции, отображается срок следующей сверки на 30 января следующего года и история записей выбранной карточки. Дата в будущем отклоняется. Повторно импортируйте **изменённую** разрешённую книгу: новая редакция показана без отметки о сверке; прежняя запись остаётся в истории. Повторный импорт неизменённого файла редакцию не увеличивает. Если ранее сверенная карточка не переимпортирована, проверьте на локальных датах 29, 30 и 31 января: статус соответственно «Сверка зарегистрирована», «Сверить сегодня», «Срок сверки прошёл». Отметка о сверке не появляется в JSON-проекте и в ответе `/api/pu66/{ключ}/scheme`.

## Нормативные документы и смена редакции

Используйте свои PDF стандартов только локально; в публичных тестах — синтетические файлы.

1. «Реестры» → «Нормативные документы» → выберите `GOST-R-52290-2024.pdf`: поля «Обозначение» и «Редакция» заполняются как `ГОСТ Р 52290` и `2024`, «Назначение» — изображения знаков. Укажите дату введения и нажмите «Проверить документ»: «Станет действующей редакцией этого документа». Добавьте — появятся запись «Редакция 2024 · действует» и имя резервной копии.
2. Повторно выберите тот же файл и проверьте: «Этот PDF уже есть в библиотеке», кнопка добавления недоступна.
3. «Открыть PDF» открывает документ в новой вкладке.
4. В «Импорт Excel и знаков» в блоке «Знаки из PDF стандарта» уже выбрана действующая редакция стандарта знаков; нажмите «Извлечь знаки из PDF» (или раскройте «Загрузка знаков из ZIP (прежний способ)», где она выбрана в поле «Документ из библиотеки», и загрузите ZIP). Просмотрите изменения: у изменённых знаков текущее и новое изображения стоят рядом, знаки со сменой только редакции считаются отдельно. 5. Добавьте условную «следующую» редакцию (любой другой PDF) с датой введения в прошлом: прежняя редакция отмечается «заменён редакцией …», а раздел документов и импорт знаков предупреждают, что каталог загружен по прежней редакции. На листе проекта с закреплёнными знаками появляется предупреждение о закреплении по устаревшей редакции.
6. С датой введения в будущем новая редакция отмечается «вводится с …», действующей остаётся прежняя.
7. Попробуйте удалить редакцию, с которой сверен импорт знаков: удаление отклоняется. «Актуальность подтверждена сегодня» записывает сегодняшнюю дату и снимает напоминание.

## Проверка создания нового проекта

С 30.09.2026 новая схема начинается только с карточки ПУ-66 из локального реестра; ручного ввода идентификатора нет.

### Без карточек в реестре

На чистой базе (например, `TOD_DATABASE_PATH` на новый файл) откройте «Проекты» → «Новый проект».

1. Вместо формы показано «В локальном реестре нет карточек ПУ-66 — начать новый проект невозможно», кнопки «Импортировать ПУ-66» и «Проверить снова». Полей размеров и кнопки «Создать проект» нет.
2. «Импортировать ПУ-66» открывает «Реестры» → «Импорт Excel и знаков» у блока импорта ПУ-66. После импорта вернитесь в «Проекты»: форма с поиском карточки появляется без перезагрузки страницы.
3. Остановите локальный API и обновите страницу: форма сообщает, что реестр ПУ-66 недоступен и начать новый проект невозможно. Вкладки «Мои проекты» и «Открыть файл» по-прежнему доступны.

### Создание проекта из карточки ПУ-66

Импортируйте учебные книги (`npm run samples:pu66`, затем «Реестры» → «Импорт Excel и знаков»). В «Проекты» → «Новый проект»:

1. Пока карточка не выбрана, кнопка «Создать проект» недоступна, форма просит выбрать карточку.
2. Введите в «Поиск карточки» `24 км 7 пк`: ожидается «Найдено: 1 из N». Проверьте также `24/7`, `озерная` (буква «ё» не важна) и `2 км` — последний запрос не находит переезды на 12 и 24 км.
3. Выберите карточку `90002:24:7`: появляется блок «Будет закреплено в проекте» с идентификатором, местом, подписью оси, дорогой «Учебная дорога Б», шириной и номером редакции. «Выбрать другую» снимает выбор, и кнопка «Создать проект» снова недоступна.
4. Введите условное название участка, фронт `18,5` м, отвод `8` м, буфер `12` м. Пока не выбрано «Вне населённого пункта» или «В населённом пункте», «Создать проект» недоступна. Выберите «В населённом пункте»: подставятся скорость на подходе `60` и скорость в зоне `40`; затем «Вне населённого пункта»: `90`, ступени `70`, `50`, `40`. Нажмите «Создать проект». Выбран Б.34, ноль объектов и знаков; размеры Б.33 показаны как «не заполнено». На этапе «Исходные данные» указано «локальная редакция № 1»; на листе этапа 4 видна «Учебная дорога Б».
5. На этапе 2 расстояния уже подставлены (300/250/150/50 м) с пометкой «по нормативу»; задайте «Знак скорости в зоне работ 3.24» = `45` и примените, на этапе 4 внесите описание работ, на этапе 3 добавьте ручную надпись: параметры и надпись появляются в проекте, история отмены работает, кнопки исходного JSON нет.
6. «Сохранить проект», перезапустите приложение и откройте проект через «Мои проекты»: редакция № 1 доступна, зона Б.33 пуста. «Скачать файл проекта (JSON)»: `schemaVersion: 9`, `parameters.location: "out"`, `approachSpeedKmh: 90`, `source.kind: "created-in-editor"`, `crossing.source: "local-pu66"`, `snapshot` содержит шесть разрешённых полей, `parameters.workZones.b33: null`.
7. В новой форме с той же карточкой задайте фронт `30` м: предварительно выбран Б.33 и показано предупреждение о пограничном случае. Фронт `0` или скорость `-1` форма отклоняет; открытый проект и черновик не меняются.
8. Если между выбором и созданием карточка была переимпортирована с изменениями, создание останавливается с сообщением о новой редакции; проверьте данные и нажмите «Создать проект» снова.

В созданном проекте попробуйте изменить длину Б.34 на `31` м: применение сообщает об ошибке несоответствия варианту — для другого варианта создайте новый проект. Новый проект держится только в памяти браузера до локального сохранения или скачивания; переход к другому проекту с несохранёнными правками требует подтверждения. Выбор карточки не означает её сверки.

Проекты, созданные до 30.09.2026 с ручным идентификатором (`crossing.source: "entered-by-editor"`), и импортированные v1 открываются как раньше; карточку к ним закрепляют на этапе «Исходные данные».

Экспортируйте JSON из автономного редактора и сохраните резервную копию до теста. Ключ `localStorage` старого HTML-прототипа напрямую этим приложением не читается: нужен именно сохранённый JSON-файл. ## Если что-то не работает

- `npm ci` показывает `EBADENGINE` с Node 26.7.0: обновите репозиторий командой `git pull --ff-only`, затем выполните `npm ci` снова. Начиная с исправления прямого запуска поддерживаются Node 24.12+ и 26.7+ в пределах соответствующих основных версий. Предупреждения `deprecated` для косвенных зависимостей сами по себе не останавливают установку.
- `npm run dev` сообщает `ERR_MODULE_NOT_FOUND` для `src/domain/model`: проверьте, что обновились `src/domain/local-projects.ts` и `src/domain/model.ts`, запустите `npm run check:runtime`. Эта проверка должна пройти до запуска интерфейса и не обращается к вашей рабочей SQLite.
- `node` или `npm` не распознаётся: завершите установку поддерживаемой версии Node.js и откройте новый терминал; проверьте `node --version`.
- `npm ci` сообщает о несовпадении `package.json` и lockfile: убедитесь, что вы на актуальной ветке `main` и локально не меняли эти файлы. Для теста используйте чистый клон.
- Страница не открывается: откройте `http://127.0.0.1:5173/` и проверьте, что оба процесса запущены. Порты 4100 и 5173 фиксированы: если один из них занят, остановите программу, занявшую порт, и повторите запуск. Для `preview` нужен свободный порт 4173.
- Блок реестров показывает ошибку: проверьте вывод локального API в терминале и наличие прав на запись в `private-data/`. Не прикладывайте файл базы к публичному обращению.
- Импорт не проходит: убедитесь, что выбран JSON проекта с `v: 1` или `schemaVersion: 2–9`, а не HTML-файл прототипа. Сверьте поле из сообщения об ошибке и проверьте исправный пример из репозитория.

При сообщении об ошибке полезно записать ОС, браузер, версии Node и npm, SHA коммита (`git rev-parse --short HEAD`), шаги воспроизведения, ожидаемый и фактический результат. Для публичного отчёта используйте обезличенный пример; не прикладывайте реальные карточки переездов, персональные данные и служебные файлы.

## Регрессии CR4: документы и закреплённые PNG

Автоматические проверки используют только вымышленные PDF и программно нарисованные PNG. Они проверяют изменение всех восьми полей сведений библиотеки после просмотра, изменение во время резервного копирования и смену даты расчёта: запись отменяется, PDF не появляется. API возвращает 409; ZIP с документом другого назначения отклоняется с 400. Смена назначения, редакции или удаление выбранного документа во время резервного копирования также не записывает каталог.

Для ручной приёмки на отдельной базе:

1. Просмотрите добавление новой редакции PDF. В другой вкладке исправьте дату введения или редакцию прежнего документа. Подтверждение первого просмотра должно потребовать нового просмотра без добавления PDF.
2. Добавьте документы назначения «Изображения знаков» и «Правила применения». Для ZIP в списке библиотеки должен быть только основной документ знаков; его изменение не должно быть отдельным источником ZIP.
3. Загрузите вымышленный PNG, закрепите редакцию в проекте. Обновите тот же код изображением других пропорций. Старый проект должен сохранить прежние размеры и PNG; повторное закрепление — получить новые. Откройте другой проект с иной закреплённой редакцией и проверьте пропорции на листе.
4. При отсутствии закреплённой редакции лист сообщает об отсутствии PNG и блокирует выгрузку; текущий PNG того же кода не подставляется.

Серверные тесты проверяют исторические размеры после исключения кода из активного каталога, 400 для неверной редакции и 404 для отсутствующей. Браузерный сценарий дополнительно задерживает ответ прежней редакции и проверяет, что после нового закрепления пропорции остаются актуальными.

## CR5: копии восстановления в нескольких окнах

Используйте вымышленный проект и два окна одного экземпляра программы; рабочие данные не прикладывайте к публичному отчёту.

1. В первом окне измените параметры, оставьте часть ввода неприменённой и дождитесь надписи «копия восстановления записана».
2. Во втором откройте «Проекты»: у этой копии написано «открыта в другом окне», кнопки «Восстановить» и «Удалить копию» недоступны. Обход через API также даёт 409; список обновляется каждые 20 секунд.
3. Перезагрузите первое окно. Обновите страницу второго и восстановите копию: применённые правки и неприменённый ввод сохранились. Копия теперь защищена от первого окна. Примените ввод и сохраните проект: создаётся редакция, копия удаляется.
4. Для аварийного сценария завершите процесс браузера без штатного закрытия страницы. После запуска подождите до двух минут и обновите страницу: копия доступна. Не завершайте сервер SQLite ради проверки вкладок.
5. При возвращении приостановленного окна после передачи копии другое окно сохраняет владение; старые запись, удаление и продление отклоняются, правки прежнего окна остаются в памяти. Используйте сохранение отдельного проекта после применения ввода, если нужно сохранить этот вариант.
6. Для импортированного старого JSON в инструментах разработчика проверьте PUT `/api/recovery/{id}`: первый содержит `originalJson`, следующий — `sourceSha256` без исходного текста. Ответ содержит только версию, дату и хеш. JSON-экспорт и восстановленная схема содержат исходный текст полностью. POST `/heartbeat` не передаёт схему и не меняет версию копии.

Автоматически: тесты RecoverySession без Vue; SQLite/API — живой владелец, продление, истечение ровно на границе, два подключения, контрольная версия после захвата, источник и миграция v12 → v13; Chromium — две вкладки и неприменённый ввод. Срок активности — координация окон, а не гарантия работы браузера в фоне.

## Первый блок рефакторинга: А3

Автоматически: `npm run check` включает `check:architecture`, негативные примеры зависимостей/циклов, semantic-path и UI-маппинг, golden fingerprints и SHA-256 рисунков пяти старых вымышленных проектов. Baseline и пределы проверки — [контракты рефакторинга](docs/refactoring-contracts.md). Golden snapshots сняты до А3; при чистом переносе их не обновляют.

В браузере проверить:

1. Создать учебный проект, открыть «Проверка и лист» и нажать «Перейти» у места работ и реквизитов. Должен открыться прежний этап и первое пустое поле с фокусом.
2. Перейти к проверке размерной цепочки и условий Б.34: открывается соответствующий этап, заголовок раздела получает фокус, если конкретного поля нет.
3. Начать правку объекта и повторить переход к заблокированному полю: ввод сохраняется, показана причина и открывается этап объектов.
4. Поставить доступные отметки «Проверено», сохранить и открыть проект после обновления. Сам перенос модулей не снимает отметки; изменение проверяемых значений снимает соответствующую отметку.
5. На своих проектах Б.33/Б.34 сравнить предпросмотр, печать A4 и PNG, включая табличку 8.2.1 и закреплённые изображения. Расстояния, тексты, пропорции и состав листа должны совпадать.

А3 не требует миграции базы и не меняет формат файла. Новая Windows-сборка и её испытание на рабочем месте — отдельная ручная контрольная точка.

## Первый блок А4: редакции и запоздалые ответы

Автоматически: `npm run check` проверяет SaveProjectRevision / RestoreProjectRevision независимо от Vue/HTTP, типизированные ошибки адаптера и Vue lifecycle с управляемыми задержками. Проверяются смена сессии при том же id, новые правки и неприменённый ввод во время записи/возврата, сохранение отдельной копии, конфликт и повтор, отмена подтверждения, задержка recovery перед возвратом и при удалении, undo/redo. `npm run test:e2e` проверяет задержку ответа SQLite, блокировку ввода, повтор неизменённой записи, возврат с сохранением всех версий и реальный 409.

1. Откройте вымышленный проект, примените правку и сохраните. Отмена и повтор остаются доступны; повторное сохранение без изменений не добавляет версию.
2. Примените другую правку и сохраните. В «Мои проекты» → «Версии» вернитесь к первой версии: она записывается новой, прежние остаются. История undo/redo начинается заново.
3. Откройте один проект в двух окнах. Во втором измените и сохраните его, затем в первом примените свою правку и попробуйте сохранить: конфликт не затирает ввод и undo/redo. Обновите список или сохраните как новый проект; исходный не перезаписывается.
4. При медленном ответе обычные поля и кнопки записи заблокированы. Программные изменения во время запроса и смена сессии проверяются Vue-тестами: новые правки/ввод остаются открытыми, старый ответ не меняет новый проект. При изменении во время предварительной записи recovery возврат требует повторного подтверждения.

Блок А4 не менял формат JSON и SQLite (на момент А4 — v7 и v13; текущий формат проекта — v9) и нормативные правила. Первый блок А4 дополнен разделением оболочки ниже; Windows exe и предметная приёмка выполняются отдельно после слияния.

## Второй блок А4: переходы без потери работы

1. Откройте вымышленный проект. На этапе 2 измените расстояние, оставьте его неприменённым. Посетите этапы 1 и 3, «Проекты», «Реестры» и «Справка»; вернитесь на этап 2. Поле содержит прежний ввод, сохранение заблокировано. Примените его, внесите и примените вторую правку, затем проверьте отмену и повтор после переходов.
2. На этапе 3 выберите объект, измените его свойства без применения. Посетите другие экраны и вернитесь: выбран тот же объект, свойства сохранены, «Применить объект» доступно. После применения работают undo/redo.
3. На этапе 4 проверьте переход «Перейти» и печать A4. Лист должен занимать одну страницу; посторонние экраны и панели в печать не входят. Повторите навигацию при узком окне.
4. Проверьте стартовую вкладку «Мои проекты», контекстную справку и импорт знаков/ПУ-66: изменения каталогов обновляют редактор, открытый проект остаётся прежним.

Два браузерных сценария переходов прошли до переноса App.vue и после него. Они проверяют неприменённый ввод, выделение, undo/redo и единственный sessionId recovery. Unit-тесты навигации проверяют запоздалый стартовый список и контекст справки. Приёмка Windows exe выполняется отдельно после слияния; А4 продолжается предметными сценариями и серверными адаптерами, следующий функциональный блок — П3.

## ОДМ и ГОСТ Р 58350 после первой приёмки

Проверка повторного запуска локальной базы выбирает проверенные порты ниже временного диапазона Windows: пара, полученная через `listen(0)`, может быть занята исходящим HTTP-соединением между проверкой и запуском. Тест пропуска занятого порта проверяет переход к доступному порту, не требует ровно соседний номер. Рабочая логика запуска не меняется.

- Отдельный расчёт таблицы Д.1 проверить на длинах участка 49/50/300/301 м и интенсивностях 249/250/500/501 авт/ч: неизвестные длина/интенсивность не определяют строку таблицы. Эти длины не вводятся как фронт переезда. Матрица специалиста проверяется по сценариям в начале документа; неподтверждённая длина участка оставляет подсказку неприменимой кнопкой.
- Пример: фронт 25 + отгон 15 + буфер 10 = 50 м при 200 авт/ч. Профиль переезда предлагает знаки; предупреждение требует отдельного обоснования по таблице Д.1. Сборка возможна при прочих выполненных условиях; выпуск требует ручной предметной сверки. Прежний автоматический отказ по сумме 50 м отменён повторной приёмкой.
- Подтверждение старого п. 5.4.4 в том же PDF требует повторной сверки п. 6.4.4. Значение старого источника не применяется; журнал сохранён. Учебное изменение к И.1 снимает подтверждение; поправка к 4.1 его не затрагивает.
- Проверить составителем видимость встречного автомобиля по ГОСТ Р 52289, отдельно видимость регулировщика, дневные работы, ограничения скорости и постоянное присутствие.
- Старые JSON открываются с прежними объектами и рисунком. Обновлены только отпечатки исправленных ручных проверок и блокировки условий; SHA-256 рисунка пяти исходных примеров сохраняется.
- В ПУ-66 категория II предлагает двух-/трёхполосную строку; строка другой категории требует проверки полос и не предлагает кнопку подстановки для иной схемы.
